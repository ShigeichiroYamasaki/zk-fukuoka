# 応用編：ZK属性証明で個人情報の保管を減らす

更新日：2026年10月10日

## この教材で考えること

ランサムウェア対策というと，侵入を防ぐことや暗号化されたデータを復旧することに目が向きます．しかし，攻撃者がネットワークへ侵入して個人情報を持ち出した場合，データを暗号化せずに公開を脅す攻撃でも，被害は深刻になります．IPAは2026年10月の注意喚起で，不要な情報を持たず，保有情報を必要最小限に見直すことを勧めています．[IPAの注意喚起](https://www.ipa.go.jp/security/security-alert/2026/alert20261009.html)

この教材では，ZK証明を「ランサムウェアを止める道具」としてではなく，**サービスが本人確認情報を複製して保管する必要を減らす道具**として使います．攻撃者がサービスのデータベースを持ち出しても，そこに氏名や生年月日，本人確認書類の画像がなければ，そのサービスから直接漏れる情報を減らせます．組織が利用目的に照らして必要な情報だけを集め，保管期間を限るというデータ最小化の考え方とも合います．[NISTのデータ最小化の定義](https://csrc.nist.gov/glossary/term/minimization)

::: warning この教材の範囲
この教材は設計・実装を考えるための学習例です．ZK証明は侵入，暗号化，情報窃取を防止せず，保有する情報をすべて不要にするものでもありません．必要なアクセス制御，多要素認証，ネットワーク分離，バックアップ，監視，脆弱性対応を別途実施してください．実データや本人確認書類は使わず，架空データで演習します．
:::

## 想定するサービス

地域の会員向けオンラインサービスが，年齢条件を満たす会員に限定コンテンツを提供するとします．従来方式では，サービスが氏名，生年月日，本人確認書類の画像を受け取り，データベースやバックアップに保存してしまうことがあります．しかし，このサービスに必要なのは「有効な会員であり，18歳以上である」という判定だけです．

資格発行者が適切な本人確認を行い，年齢条件や有効期限を含む電子資格情報を利用者に発行します．利用者のウォレットは，資格情報が発行者の署名を持ち，有効期限内であり，年齢条件を満たすことをZK証明します．サービスは証明を検証し，コンテンツへのアクセスを許可します．サービス側は生年月日や本人確認書類を受け取らず，ログイン・不正利用対策に必要な最小限の仮名IDだけを保持する設計を検討します．

| 項目 | 従来方式の例 | ZK属性証明を使う設計例 |
| --- | --- | --- |
| サービスが受け取るもの | 氏名，生年月日，書類画像，判定結果 | 「有効会員かつ18歳以上」の証明，必要最小限の仮名ID |
| サービスのデータベース | 本人確認情報を会員記録に複製する場合がある | 生年月日や書類画像を保存しない |
| 資格発行者 | 本人確認を実施 | 本人確認を行い，資格を発行・失効管理する |
| 漏えい時に直接露出しうる情報 | 保管内容に応じて本人確認情報まで含む | サービス側の保管項目に限定される |

この比較は，発行者の情報まで消えるという意味ではありません．発行者が本人確認情報を保持するなら，発行者のシステムは重要な保護対象のままです．目的は，個人情報を多くのサービスへ複製する構造を減らし，漏えい箇所ごとの被害範囲を小さくすることです．

## 証明する関係

発行者の公開鍵を $pk_I$，秘密の資格情報を $cred$，利用者の秘密値を $s$，現在時刻を $t$ とします．概念上，証明したいのは次の関係です．

$$
\exists(cred,s):\quad
\mathrm{VerifyCred}(pk_I,cred)=1
\;\land\;
\mathrm{age}(cred)\geq 18
\;\land\;
\mathrm{validUntil}(cred)\geq t
$$

実際の回路では，資格情報の署名検証，年齢条件，有効期限，失効確認を，選んだ暗号方式と資格情報形式に合わせて定義します．年齢や会員状態などを資格発行者が正しく確認したことは，発行者の業務と監査の責任です．ZK証明は，誤った確認を正しくするものではありません．

一度だけ使える特典を扱う場合は，資格の秘密値とサービス名・期間からスコープ付きnullifierを作り，同じ期間内の二重利用を拒否できます．同じスコープ内で同じ資格を使うと同じnullifierが現れるため，利用者の識別情報を公開せずに再利用を検出できます．ただし，nullifierのスコープを広くしすぎると利用履歴が結び付きます．このサービス例では，通常のログイン認証そのものをZKに置き換えるのではなく，年齢・会員資格の開示を減らすことに焦点を絞ります．

## 情報の流れと信頼境界

| 段階 | 処理 | サービスに渡る情報 | 保護すべき情報 |
| --- | --- | --- | --- |
| 1. 資格発行 | 発行者が本人確認を行い，資格情報を利用者へ発行 | なし | 発行者が取り扱う本人確認情報，発行記録 |
| 2. 証明生成 | 利用者の端末が資格情報から条件充足の証明を生成 | まだ送信しない | 資格情報，秘密値，端末内データ |
| 3. 検証 | サービスが証明と公開条件を検証 | 証明，発行者公開鍵，必要なら期間限定nullifier | 氏名・生年月日・書類画像は送信しない |
| 4. アクセス | 検証成功時にサービスがアクセスを許可 | 仮名ID，アクセス制御に必要なイベント | ログに個人情報や秘密値を残さない |
| 5. 失効 | 発行者が失効情報を更新し，検証側が反映 | 失効確認用の公開情報 | 失効理由や本人との対応表 |

ZK証明を使っても，IPアドレス，時刻，端末識別子，アクセス頻度，公開されたnullifierなどから利用者が推測される可能性があります．証明の入力・出力だけでなく，ログ，分析ツール，バックアップ，サポート画面，委託先へのデータ連携もデータフローに含めて評価します．

## 演習：漏えい時に見えるデータを比較する

### 用意するもの

- 架空の利用者データ10件（氏名，生年月日，書類画像の有無，仮名ID）
- 従来方式の会員データベースと，ZK属性証明方式のサービスデータベース
- 「攻撃者がデータベースを読み出した」というインシデント想定

### 手順

1. 従来方式では，サービスが実際に必要とする項目と，慣例で保存している項目を分けます．
2. ZK方式では，発行者，利用者の端末，サービスの役割を決め，どの情報をどこが持つかを表にします．
3. 同じ利用許可判定を，従来方式は保存済みの生年月日から，ZK方式は資格証明の検証から行う設計にします．
4. データベースを読み出された想定で，攻撃者が直接得られる情報を両方式で数えます．氏名・生年月日・書類画像などの項目数と，該当する利用者数を比較します．
5. 期限切れ資格，失効済み資格，年齢条件を満たさない資格，改ざん証明を拒否する試験を設計します．
6. 発行者側が侵害された場合，証明生成端末が侵害された場合，ログやバックアップに情報が残った場合も別々に検討します．

この演習では，ZKを使ったこと自体を成果にしません．**サービスの機能を保ったまま，サービス側の個人情報の複製と漏えい時の露出項目を実際に減らせたか**を評価します．

### 完了条件

- アクセス判定に必要な情報と，保存しない情報を理由とともに説明できる．
- サービス側のデータベースから，氏名・生年月日・本人確認書類画像を取り除く設計を示せる．
- 有効期限切れ，失効，条件不一致，証明改ざんを拒否する試験を定義できる．
- 発行者・サービス・利用者端末それぞれに残る情報と信頼上の前提を示せる．
- ログやバックアップを含むデータフローを確認し，ZKで隠れないメタデータを列挙できる．
- ZKは侵入防止や復旧の代替ではなく，情報最小化を通じて漏えい時の影響を抑える補助策だと説明できる．

## 実運用で併用する対策

この設計が扱うのは，主に「漏えいした場合に何が出ていくか」です．ランサムウェアの侵入・暗号化・拡散には，別の対策が必要です．IPAのランサムウェア対策情報にある予防・検知・復旧策や，組織のインシデント対応計画と組み合わせます．[IPA：ランサムウェア対策特設ページ](https://www.ipa.go.jp/security/anshin/measures/ransom_tokusetsu.html)

個人情報保護委員会のガイドラインが示す漏えい等への対応や報告・本人通知の要否も，ZK証明の採用によってなくなるわけではありません．事業で扱う場合は，適用される法令・ガイドラインと委託関係を確認してください．[個人情報保護委員会：漏えい等の対応とお役立ち資料](https://www.ppc.go.jp/personalinfo/legal/leakAction/)
