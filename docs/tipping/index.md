# 応用編：JPKIワレットでプライバシーを守るステーブルコイン投げ銭

更新日：2026年10月7日

JPKIを使った本人確認とゼロ知識証明を組み合わせ，支援者の氏名やウォレット対応関係を一般公開しない形で，ミュージシャンへステーブルコインで投げ銭する仕組みを設計します．ここで目指すのは**法令上の義務を免れる匿名化ではありません**．一般の閲覧者に対するプライバシーを高めつつ，規制対象となる事業者が必要な本人確認・取引記録・法令に基づく照会対応を行える設計を学びます．

::: warning 教材の範囲
これは制度・実装上の論点を学ぶための設計例であり，法律意見，登録要否の判定，実運用可能な決済サービスではありません．実運用前に，取り扱うトークンの法的分類，サービスの役割，資金の流れ，AML/CFT，税務，個人情報保護について，日本の弁護士・税理士と所管当局に確認してください．演習ではテストネット用トークンと架空データだけを使います．
:::

このページは**設計演習の仕様案**です．JPKI連携，匿名資格の発行，ステーブルコインの送金・精算を実行するコードや，法令適合性を確認したサービスは含みません．

## 何を作るか

支援者はJPKIで本人確認を受けた後，キャンペーン単位の資格をワレットに受け取ります．ワレットはその資格を使い，「有効な参加資格を持つ」「今回のキャンペーンで二重に使っていない」「決められた上限内の支援である」という条件をゼロ知識証明します．公開ページに氏名や支援者のウォレット一覧を載せず，受託した登録事業者は本人確認情報と取引記録を法令・契約に従って管理します．

この例の「匿名」は**公衆に対する仮名性**です．決済事業者，発行者，受取人，法令上の権限を持つ機関のすべてから取引を隠すことは目標にしません．JPKIそのものが匿名クレデンシャルやブロックチェーン用ワレットを発行するわけではなく，JPKIの本人確認結果を別の資格発行・検証サービスへ安全に連携する構成は，別途の制度・契約・セキュリティ確認が必要です．

## 登場する主体と情報の流れ

| 段階 | 主体と処理 | 公開される情報 | 事業者が保持する情報 |
| --- | --- | --- | --- |
| 1. 本人確認 | 支援者がJPKI対応の本人確認サービスを利用する | なし | 確認に必要な本人情報と確認記録 |
| 2. 資格発行 | 本人確認サービスまたは委託先が，キャンペーン・期限・上限に結び付く資格を発行する | 資格の発行件数など，集計値のみ | 発行・失効記録．本人と資格の対応は分離保管できるか検討 |
| 3. 支援の証明 | ワレットが資格，秘密鍵，支援額を使い，二重利用でないことと上限内であることを証明する | キャンペーンID，証明，必要最小限の決済情報 | 支援者，金額，日時，送付先などの取引記録 |
| 4. 決済と精算 | 登録要否を確認した決済事業者が対応するステーブルコインを処理し，ミュージシャンへ精算する | 精算合計や検証結果．個人との対応は公開しない設計を目指す | 個々の支援・入出金・本人確認・会計記録 |
| 5. 検証 | 誰でも公開証明とキャンペーン条件を確認する | 集計額が正しいこと，許可されたキャンペーンであること | 適法な照会・監査に必要な対応記録 |

| 情報 | 支援者 | ミュージシャン | 決済・本人確認事業者 | 一般の閲覧者 |
| --- | --- | --- | --- | --- |
| 氏名と本人確認記録 | 自分の情報を確認 | 原則として不要 | 必要な範囲で確認・保管 | 公開しない |
| 個々の支援額と送金記録 | 確認できる | 精算方法によって個別額または合計を確認 | 法令・業務上必要な記録を保持 | 個人との対応を公開しない |
| ゼロ知識証明 | 生成する | 必要な精算情報を確認 | 適合性と記録を確認 | 公開部分を検証できる |

## 何を証明するか

キャンペーンIDを $c$，資格に対応する秘密値を $s$，支援額を $a$，資格発行者の公開鍵を $pk_I$ とします．回路・証明系の関係は概念的には次の形です．

$$
\exists(s,\,\mathrm{cred},\,r):\quad
\mathrm{VerifyCred}(pk_I,\mathrm{cred},s,c)=1
\;\land\;
0 < a \leq a_{\max}
\;\land\;
N=H(s,c)
$$

ここで $N$ はキャンペーンごとのnullifier（同じ資格の二重利用を見つける識別子）です．同じキャンペーンでは同じ $N$ が出るため，再利用を拒否できます．別キャンペーン間で同じ利用者だと公開情報から結び付かないよう，キャンペーンIDをハッシュ入力に含めます．実際の資格署名とハッシュは，回路効率・安全性・失効方法を評価して選定する必要があります．この式だけで本人確認の正しさ，支援者の意思，ステーブルコインの法的適格性が自動的に保証されるわけではありません．

決済を台帳で集計する演習では，各支援について「有効な一回限りの資格」と「額の上限」を検証し，公開する集計額が個々の支援額の和に等しいことも証明できます．個々の支援を単純に公開チェーンへ直接送金すると，送信元・送信先アドレス，金額，時刻が分析可能なまま残ります．ゼロ知識証明だけでは，その公開記録を匿名化できません．

## 何を隠せて，何が残るか

| 項目 | 公開型チェーンへ直接送る場合 | 本教材のプライバシー目標 |
| --- | --- | --- |
| 支援者の氏名 | 取引に氏名が含まれなくても，他の公開情報との照合で推定される場合がある | 一般公開しない．ウォレットと本人の対応付けを抑える |
| 送信元・送信先アドレス | 公開 | 個々の支援者アドレスとミュージシャンを公開データ上で直接結ばない構成を検討 |
| 個々の金額・時刻 | 公開 | 一般向けには集計または範囲だけを公開できるか検討 |
| 決済サービスの記録 | 事業者の関与がなければ存在しない | 適用される規制・契約・会計上必要な記録を保持 |
| 法令に基づく調査 | 公開情報に加え，事業者の記録が使われる場合がある | 適法な照会・監査に対応可能な運用を残す |

公開情報の量を減らすほど，データ可用性，監査可能性，誤送金対応，利用者保護との調整が難しくなります．単一の運営者だけが復元できる秘密鍵を置けば解決する，という単純な設計にはしません．鍵管理，複数者承認，保存期間，開示条件，異議申立て，運営者停止時の精算方法を仕様化します．

## 法令順守を設計条件にする

- ステーブルコインは一括りではありません．日本法上の電子決済手段に該当するか，発行者・償還者・取引経路が誰かを個別に確認します．金融庁は，電子決済手段等取引業などを国内で業として営む場合の登録制度を案内しています．
- 主催者が利用者から資金を受け取り，保管し，送金・交換・媒介するなら，名称が「投げ銭」でも規制対象業務に該当し得ます．自己判断でカストディや交換機能を作らず，必要な登録を有する事業者のサービスを使う前提で法的検討を行います．
- 暗号資産・電子決済手段の移転には，対象事業者・移転経路に応じて送付人・受取人の通知や記録などの義務が関係します．ゼロ知識証明は，これらの義務を消したり，適用除外を作ったりする道具ではありません．
- JPKIは本人確認・電子署名の基盤です．マイナンバーそのものを資格の識別子やチェーン上の値として使わず，カード秘密鍵や個人番号をサーバ・回路・公開ログへ送らない設計にします．JPKIの利用方法・委託・資格発行が適切かを確認します．
- 「投げ銭」が純粋な贈与か，演奏・限定配信・特典などの対価かで，契約・税務上の扱いが異なる可能性があります．ミュージシャン側は受領時価の記録，帳簿，申告区分を税理士と確認します．
- 制裁対象者・不正資金・詐欺への対策と，疑わしい取引の検知・届出など，関係事業者に適用されるAML/CFT運用を設計します．資格証明が「利用者は誰でもよい」という許可証にならないようにします．

金融庁の資料は，ステーブルコインの移転が取引経路の追跡を可能にするトラベルルールや，登録制度と関係することを説明しています．制度は更新されるため，実装時に必ず現行の法令・監督指針を確認してください．

## 演習の段階

1. **公開チェーンの基準例**：テストトークンを支援者アドレスからミュージシャンへ直接送金し，ブロックエクスプローラで金額・時刻・アドレスが見えることを確かめます．
2. **資格検証**：架空のJPKI確認結果から発行したテスト資格について，キャンペーンID，期限，上限を含む署名検証を実装します．実際のJPKI連携は行いません．
3. **二重利用防止**：資格秘密値とキャンペーンIDからnullifierを作り，同じキャンペーンで二度目の支援を拒否します．
4. **ゼロ知識化**：資格・秘密値・支援額を秘密入力，キャンペーン・上限・nullifierを公開入力とする回路を作ります．「本人情報を含めない」ことと，証明が成立することを別々にテストします．
5. **集計と監査**：複数の支援額の和が精算額と一致する証明を作ります．公開閲覧者向けのデータと，事業者が保存する取引記録を別のデータフローとして文書化します．
6. **脅威・制度レビュー**：本人確認のなりすまし，資格の貸し借り，nullifierの相関，運営者漏えい，誤送金，事業者停止，法令照会を脅威表にし，未解決なら本番化しない判定にします．

### 合格条件

- 無効・期限切れ・失効済み資格を拒否し，有効資格の同一キャンペーン内の再使用を拒否する．
- 上限超過を拒否し，公開する集計額と台帳上の精算額が一致する．
- 氏名，個人番号，電子証明書データ，秘密鍵，個別の支援者対応表が公開入力・イベント・ログに含まれない．
- 一般閲覧者に見えない設計でも，決済事業者が保有する必要記録まで消していないことをデータフロー表で説明できる．
- 実装が法令上の登録要否を解決したとは主張せず，未確認事項と専門家レビューの結果を明記する．
