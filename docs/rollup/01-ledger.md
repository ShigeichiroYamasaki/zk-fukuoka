# 1. 残高台帳と保存則

[応用編の全体像](./) · [第4回](../learn/session-04) · [次：Merkle木](./02-state)

## 何を作るか

最初に，暗号学的な証明を使わず状態遷移の正解を決めます。後で回路・コントラクトの結果と照合するための参照実装です。

アカウントは `(id, owner, balance, nonce)`。モデルのownerはAliceなどのラベルで，本実装ではL1アドレスとL2公開鍵に分けます。モデルへの呼び出しは認可済みとして扱い，署名の検証はまだ行いません。

## 預かったトークンと負債を対応させる

入金をL1で受け取ってからL2へ反映するまで，時間差があります。出金をL2から差し引いてからL1で受け取るまでも同様です。

$$V=U+B+W$$

| 記号 | 意味 |
| --- | --- |
| $V$ | L1コントラクトが預かる数量 |
| $U$ | まだL2へ反映していない入金 |
| $B$ | L2アカウント残高の総額 |
| $W$ | L2から差引済みで，L1では未請求の出金 |

手数料も外部からの直接送金もないこのモデルでは等式になります。実際のERC-20は直接送金できるので，実コントラクトでは会計上の預託額と実残高を区別し，余剰があってもユーザーへの負債を増やさない設計にします。

| 操作 | $V$ | $U$ | $B$ | $W$ |
| --- | --- | --- | --- | --- |
| 入金受取 $a$ | $+a$ | $+a$ | 0 | 0 |
| 入金をL2へ反映 | 0 | $-a$ | $+a$ | 0 |
| L2送金 | 0 | 0（変化なし） | 0（総額不変） | 0 |
| 出金要求を確定 | 0 | 0 | $-a$ | $+a$ |
| L1で出金を請求 | $-a$ | 0 | 0 | $-a$ |

## 実装する操作

- `receive(account, amount)`：入金キュー末尾へ連番で追加する。
- `consume(depositId)`：カーソルが示す次の入金だけを処理し，カーソルを一つ進める。
- `transfer(from, to, amount, nonce)`：残高，受取側の加算上限，nonceの一致を確認して送金者nonceを増やす。
- `withdraw(from, recipient, amount, nonce)`：残高を減らし，受取先を固定した出金レコードを作る。
- `claim(exitId)`：未請求であることを確認して支払い，請求済みにする。

失敗した操作で状態を一部だけ変更してはいけません。参照実装の`apply`はコピーで検査を完了してから変更を確定します。本実装のL1はrevert，オフチェーンのバッチ生成は作業用状態を使って同じ性質を保ちます。

## 実行する {#run}

<a :href="withBase('/examples/rollup/ledger_model.py')" download>ledger_model.pyを保存</a>し，Python 3.8以降で実行します。

```sh
python3 ledger_model.py
python3 ledger_model.py --test
```

<a :href="withBase('/examples/rollup/expected-demo.json')" download>期待する出力JSON</a>と比較できます。出金請求直前は `vault=100, balances=70, pending_withdrawals=30`，請求後は `vault=70, balances=70, pending_withdrawals=0` です。

このモデルには署名，ERC-20コントラクト呼び出し，証明生成，ネットワーク通信はありません。モデルで送金できたことと，本人の認可を証明できたことを区別してください。

## 合格条件

配布モデルの12件のテストでは，正常フロー，入金順序と再処理，残高不足，自己送金，nonce再使用，範囲違反，加算上限，出金再請求，出金nonce，Merkle所属，改変パス，操作記録からの再現を確認します。

追加課題として，二つの送金を逆順に実行した結果がどう変わるかを記録してください。総額が同じでも，nonceや途中の残高によって可否が変わります。
