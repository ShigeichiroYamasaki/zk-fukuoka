# 第14回:統合的視点 — 幕I〜IIIの往還
::: info 講義原稿

## 本講義の位置づけと到達目標

これまでの13回で、幕I(目的と動機)、幕II(道具立て)、幕III(統合)の3つの部を一通り学び終えた。今日は幕III最後から2番目の回として、これまで個別に読んできたGroth16・PLONK・STARKの3プロトコルを横断的に整理し、**幕Iで立てた問い・幕IIで整備した道具が、それぞれのプロトコルのどこで、どう答えを与えているか**を一覧化して振り返る。

到達目標は次の3点:

1. Groth16・PLONK・STARKが、幕Iで定義した完全性/健全性/ゼロ知識性という性質を、それぞれどう満たしているかを対比的に説明できるようになる
2. 幕IIで導入した暗号学的仮定・計算量理論的結果が、各プロトコルのどの部分で使われているかを一覧化できるようになる
3. 3プロトコルの設計思想の違いを、単なる「性能の比較」としてではなく、**幕Iの2軸(表現力・効率性)に基づく異なる最適化の選択**として理解する

新しい概念はほとんど導入せず、これまでの13回の内容を再構成し、つなぎ直すことに主眼を置く回である。

---

## 1. 幕Iの性質から振り返る

### 1.1 完全性

3プロトコルとも、正直な証明者が正しいウィットネスを持っていれば、検証者はほぼ確実に受理する(第1回で定義した基本的性質)。この点では3者に本質的な差はない。

### 1.2 健全性:Proof か Argument か

第1回で導入したProof/Argumentの区別を思い出そう。Groth16・PLONK・STARKはいずれも、計算量的に制限された証明者を想定する**Argument**である(第1回4.2節)。無限の計算能力を持つ証明者に対しては、いずれも健全性の保証を失う。この点は3者に共通するが、その健全性が依拠する仮定の種類は大きく異なる:

| プロトコル | 健全性の根拠                                                                                            |
| ---------- | ------------------------------------------------------------------------------------------------------- |
| Groth16    | q-SDHなどのペアリングベースの困難性仮定(第7回)への還元                                                  |
| PLONK      | 同じくペアリングベースの仮定(KZGコミットメントのbinding性、第8回)+ permutation argumentの健全性(第12回) |
| STARK      | ハッシュ関数の衝突耐性 + FRIの健全性(第6回、list decodingパラメータに基づく定量評価、第5回)             |

第4回のCook-Levin定理はすべてのプロトコルに共通する大前提(算術化そのものの正当化)であり、いずれのプロトコルもこの上に成り立っている。

### 1.3 ゼロ知識性

3プロトコルとも計算量的ゼロ知識(第2回の3階層のうち最も弱い、しかし実用上十分な水準)を達成する。ゼロ知識性を実現する具体的な仕掛けは異なる:

- Groth16:証明生成時にランダムなブラインディング項を導入(第11回3.2節)
- PLONK:同じくブラインディング項に加え、permutation argumentの構成そのものにもランダム性を組み込む
- STARK:FRIのコミットメントにランダムなマスキング多項式を加えることで、トレースの情報が漏れないようにする(この点は第13回では詳述しなかったが、実装上は各ステップにランダム性を追加する形で実現される)

### 1.4 知識の健全性と抽出者

第2回で導入した知識の健全性・抽出者の概念も振り返っておきたい。単純な代数的関係(Schnorr)では抽出者は2つのtranscriptからの線形代数で構成できたが(第2回4.1節)、一般計算を扱うGroth16・PLONK・STARKでは、より精巧な抽出者構成(第6回で触れたrewinding・forking lemmaの一般化)が必要になる。この技術的な複雑さの増大こそが、第2回で予告した「構造の喪失に伴う質的な困難さ」の具体的な現れである。

---

::: info 補足:安全性の根拠とゼロ知識性の水準
1.2節のGroth16の行は修正が必要です。原論文は知識の健全性を汎用双線形群モデルで証明しており、単純なq-SDHへの還元ではありません。また、Groth16の原論文は**完全ゼロ知識性**を示しているため、1.3節の「3者とも計算量的ゼロ知識」という説明で水準を一律に分類しないでください。[Groth16原論文](https://iacr.org/archive/eurocrypt2016/96650272/96650272.pdf)を参照してください。

非対話型のPLONK・STARKでは、表の要素に加えてFiat-Shamir変換とROMの議論も必要です。STARKという方式名だけでゼロ知識性が保証されるわけではなく、トレースのマスキング等を含む具体的構成を確認します。permutation argumentの検査用乱数と、秘匿のためのブラインディングも別の役割です。抽出者の構成もすべてがrewindingやforking lemmaの一般化とは限らず、証明系と安全性モデルに依存します。[第11回](./session-11)・[第12回](./session-12)・[第13回](./session-13)の補足も参照してください。
:::

## 2. 幕IIの道具立てから振り返る:プロトコル横断マップ

以下の表は、これまで学んだ道具が、それぞれどのプロトコルのどの部分で使われているかを一覧化したものである。

| 道具(講義回)                           | Groth16                                          | PLONK                                              | STARK                                |
| -------------------------------------- | ------------------------------------------------ | -------------------------------------------------- | ------------------------------------ |
| 有限体・多項式・Schwartz-Zippel(第3回) | QAP評価点での恒等性検査の基盤                    | ゲート制約・permutation argumentの多項式検査の基盤 | 制約の線形結合による集約の基盤       |
| 算術化:R1CS/QAP/AIR(第4回)             | QAP                                              | PLONKishな算術化(セレクタ多項式)                   | AIR(実行トレース)                    |
| 誤り訂正符号(第5回)                    | 直接使用しない                                   | 直接使用しない                                     | RS符号としてのトレース多項式の符号化 |
| FRI・健全性増幅(第6回)                 | 直接使用しない                                   | (FRIベースの派生実装では使用)                      | Low-Degree Testingの中核             |
| 楕円曲線・ペアリング(第7回)            | 検証等式の核心                                   | KZGコミットメントの基盤                            | 直接使用しない                       |
| 多項式コミットメント(第8回)            | KZG(暗黙的、検証式に統合)                        | KZG                                                | FRIベースのコミットメント            |
| Fiat-Shamir・ROM(第9回)                | 使用しない(トラステッドセットアップで直接非対話) | 使用する                                           | 使用する                             |
| PCP/IOP(第10回)                        | 理論的背景として                                 | IOP設計の枠組みとして明示的                        | IOP設計の枠組みとして明示的          |

この表を見ることで、**「同じ幕IIの道具箱から、プロトコルごとに異なる組み合わせが選ばれている」**という構造が視覚的に把握できる。特に、ペアリング系(Groth16, PLONK)と符号理論系(STARK)という2つの系統が、第8回で整理したコミットメントの選択を境に分岐していることが、この表全体を貫く軸になっている。

## 3. 幕Iの2軸に基づく設計思想の対比

第2回で導入した「表現力×効率性」の2軸マトリクスを思い出そう。3プロトコルはいずれも表現力の軸(一般のNP関係を扱える)では同等だが、効率性の軸の中でも、**何を最適化するかという優先順位**が異なっている。

| 優先する性質               | Groth16              | PLONK                                   | STARK                              |
| -------------------------- | -------------------- | --------------------------------------- | ---------------------------------- |
| 証明サイズ・検証速度       | 最優先(定数サイズ)   | 高い(定数サイズ、Groth16よりやや大きい) | 相対的に劣る(対数サイズ)           |
| セットアップの柔軟性       | 低い(回路ごと)       | 高い(universal & updatable)             | 最高(トラステッドセットアップ不要) |
| 長期的な安全性(ポスト量子) | 低い(楕円曲線に依存) | 低い(楕円曲線に依存)                    | 高い(ハッシュ関数に依存)           |
| 証明者の計算コスト         | 比較的高い           | 比較的高い                              | 準線形に抑えやすい                 |

**この表が伝えたい最も重要な点は、どれか一つが絶対的に「優れている」わけではなく、それぞれが異なる制約条件(信頼できるセットアップ主体がいるか、長期的な安全性が重要か、証明サイズが厳しく制限される環境か)のもとで最適な選択となる、という設計思想の多様性である。**

---

::: info 補足:比較表の読み方
2節のGroth16の「KZG(暗黙的、検証式に統合)」は構成要素の説明として正確ではありません。Groth16はQAPとペアリングを組み合わせた直接的な構成で、KZGを部品として組み込むPLONKとは区別します。ここでのPLONKはKZG型、STARKは代表的なAIR・FRI型を想定しています。

3節の表は設計上の傾向を示すもので、一般的な性能順位ではありません。STARKにはMerkle認証経路等も含まれるため、コストは一般に多重対数的と捉えます。Groth16・PLONKにも公開入力数に応じた検証コストがあり、証明者の速度は回路・実装・ハードウェア・安全性パラメータで変わります。ポスト量子安全性にも、ハッシュのパラメータと非対話化の量子モデルでの解析が必要です。演習では、同じ条件での実測と要件を根拠に選択してください。
:::

## 4. 演習:設計判断のシミュレーション

講義内で、次のような設定を学生に提示し、「どのプロトコルを選ぶべきか、理由とともに答えよ」という演習を行う:

- ブロックチェーン上でオンチェーンの検証コストを極限まで下げたい(ガス代の制約が厳しい)場合
- 新しいアプリケーションを頻繁にリリースする必要があり、その都度トラステッドセットアップをやり直す余裕がない場合
- 量子計算機の実用化を見据えて、長期的な安全性を最優先したい場合
- 証明者側の計算資源が限られており、大規模な計算を効率よく証明したい場合

これらの演習を通じて、単なる知識の確認にとどまらず、**幕全体を通じて学んだトレードオフの構造を、実践的な意思決定に応用する力**を養う。

## まとめと次回予告

今日学んだこと:

- 完全性/健全性/ゼロ知識性という幕Iの性質を、3プロトコルがそれぞれどう満たしているかを対比した
- 幕IIの道具立てが、プロトコルごとにどう選択的に組み合わされているかを一覧表で整理した
- 幕Iの2軸(表現力・効率性)のうち、効率性の軸の中でも「何を優先するか」という設計思想の違いが、3プロトコルの性能プロファイルの違いを生んでいることを確認した

次回(最終第15回)は、この講義全体の締めくくりとして、再帰的証明(recursive SNARKs)、folding schemes、GKR/sumcheckベースの新潮流を扱う。今日整理した2軸マトリクスに沿って、現在の研究がどの方向を攻めているかを展望する。
