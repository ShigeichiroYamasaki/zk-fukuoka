# 第14回:統合的視点 — 幕I〜IIIの往還

**著者名：山崎重一郎**<br>
作成日付：2026年9月27日<br>
最終更新日付：2026年9月27日

[各回の授業](./sessions) · [トピック別](./topics) · [シラバスの第14回](./#session-14) · [演習](../exercises/)

## 本講義の位置づけと到達目標

これまで，Groth16・PLONK・STARKを個別に読んできた。今日は，第1回で立てた問いへ戻って比較しよう。正しい主張を受け入れるのはどの部分か。不正を防ぐのに何を仮定するか。ウィットネスの情報を隠すには何を加えるか。**目的から構成を読み直す**ことで，幕IIの道具がそれぞれどの役割を担っているかを整理する。

到達目標は次の3点:

1. Groth16・PLONK・STARKが、幕Iで定義した完全性/健全性/ゼロ知識性という性質を、それぞれどう満たしているかを対比的に説明できるようになる
2. 幕IIで導入した暗号学的仮定・計算量理論的結果が、各プロトコルのどの部分で使われているかを一覧化できるようになる
3. 3プロトコルの設計思想の違いを、単なる「性能の比較」としてではなく、**幕Iの2軸(表現力・効率性)に基づく異なる最適化の選択**として理解する

新しい概念はほとんど導入せず，これまでの13回の内容を再構成し，つなぎ直すことに主眼を置く回である。比較対象はGroth16，原論文のKZG型PLONK，代表的なAIR・FRI型STARKとする。派生方式では構成や前提が変わるため，方式名だけで性質を決め付けない。

## 1. 幕Iの性質から振り返る

### 1.1 完全性

まず，正しいウィットネスを持つ証明者が手順に従った場合を考える。三つの方式とも，検証者が高い確率で受理することを要求する。これが第1回の完全性である。構成は異なっていても，何を保証したいかという出発点は共通している。

### 1.2 健全性:Proof か Argument か

次に，間違った主張を通そうとする相手を考える。Groth16・PLONK・STARKはいずれもArgumentであり，計算能力を制限した相手への保証を扱う。第1回5.2節の区別である。しかし，「Argumentである」という分類だけでは，どの前提で安全なのかは分からない。表では，方式ごとの根拠を分けて確認しよう。

| プロトコル | 健全性を読む際の主な前提・構成要素 |
| --- | --- |
| Groth16 | 正しく生成されたCRSのもとで、原論文は汎用双線形群モデルによる知識の健全性を示す。単純なq-SDHへの還元ではない |
| KZG型PLONK | 多項式IOPの健全性、KZGによるコミットメントの安全性、およびFiat-ShamirのROMでの解析。知識の健全性には抽出の条件も確認する |
| AIR・FRI型STARK | AIRの制約・整合性検査とFRIの健全性、Merkle木の拘束性を支えるハッシュの衝突耐性、およびFiat-ShamirのROMでの解析 |

表は安全性証明を読むための見取り図であり，仮定やモデルを列挙するだけで証明が完成するわけではない。Groth16のモデルについては[原論文](https://iacr.org/archive/eurocrypt2016/96650272/96650272.pdf)，各構成の詳細は[第11回](./session-11)・[第12回](./session-12)・[第13回](./session-13)を参照する。

第4回のCook-Levin定理と回路への帰着は，一般のNP関係を制約として扱えることの理論的背景である。ただし，個々の算術化の正しさや暗号学的な健全性は，それぞれ別に示す必要がある。

### 1.3 ゼロ知識性

健全性のための仕組みを用意すれば，秘密も守られるだろうか。ここでも二つを区別する。ゼロ知識性には，ウィットネスなしで検証者の得る情報を再現できることを示す必要がある。方式ごとに，何を乱数化し，どのモデルでシミュレーションするかを確認する。

- **Groth16**:証明生成時の新たな乱数で群要素をブラインドする。原論文は**完全ゼロ知識性**を示している(第11回3.2節)
- **PLONK**:ウィットネスを符号化する多項式や累積積多項式等をランダム化し、開示値から情報が漏れないようにする。permutation argumentを検査するためのチャレンジと、秘匿のためのブラインディングは役割が異なる
- **STARK**:トレースの評価値等の開示から情報が漏れないよう、次数上限や制約と整合するマスキングを含む構成が必要になる。透明性やFRIの使用だけでゼロ知識性が保証されるわけではない

### 1.4 知識の健全性と抽出者

第2回のSchnorrでは，同じ最初のコミットに対する二つの異なるチャレンジの受理記録から，ウィットネスを取り出した。一般の計算でも，まったく同じ操作で抽出できるだろうか。取り出したい対象が回路の割当に変わると，利用する情報や，抽出者に認めるアクセスも方式ごとに変わる。

Groth16の汎用群モデルでの解析，PLONKの多項式コミットメントを用いる構成，STARKの符号理論的な構成を，すべてrewindingやforking lemmaの一般化として説明することはできない。知識の健全性を読む際は，何が抽出されるか，抽出者にどのアクセスが許されるか，どの仮定を使うかを区別する。

## 2. 幕IIの道具立てから振り返る:プロトコル横断マップ

次は性質から道具へ視点を移そう。同じ有限体や多項式でも，どの関係を検査するために使うかが異なる。以下の表では，道具の名前を確認するだけでなく，各欄が証明生成や検証のどの作業に対応するかを説明してみよう。

| 道具(講義回)                           | Groth16                                          | PLONK                                              | STARK                                |
| -------------------------------------- | ------------------------------------------------ | -------------------------------------------------- | ------------------------------------ |
| 有限体・多項式・Schwartz-Zippel(第3回) | QAP評価点での恒等性検査の基盤                    | ゲート制約・permutation argumentの多項式検査の基盤 | 制約の線形結合による集約の基盤       |
| 算術化:R1CS/QAP/AIR(第4回)             | QAP                                              | PLONKishな算術化(セレクタ多項式)                   | AIR(実行トレース)                    |
| 誤り訂正符号(第5回)                    | 直接使用しない                                   | 直接使用しない                                     | RS符号としてのトレース多項式の符号化 |
| FRI・健全性増幅(第6回)                 | 直接使用しない                                   | 原論文のKZG型では使用しない                      | Low-Degree Testingの中核             |
| 楕円曲線・ペアリング(第7回)            | 検証等式の核心                                   | KZGコミットメントの基盤                            | 直接使用しない                       |
| 多項式コミットメント(第8回)            | KZGを部品として使わず、QAPとペアリングで直接構成                        | KZG                                                | FRIベースのコミットメント            |
| Fiat-Shamir・ROM(第9回)                | 使用しない(CRSモデルで直接非対話) | 使用する                                           | 使用する                             |
| PCP/IOP(第10回)                        | 理論的背景として                                 | IOP設計の枠組みとして明示的                        | IOP設計の枠組みとして明示的          |

共通の道具があっても，構成全体が同じとは限らない。Groth16とKZG型PLONKはペアリングを共有するが，前者にKZGの開示証明を組み込んでいるわけではない。STARKでは，表を固定するMerkle木と，低次数近接性を調べるFRIが別の仕事をしている。表の横方向と縦方向を往復して，この役割の違いを確認しよう。

## 3. 幕Iの2軸に基づく設計思想の対比

三つの方式とも，一般のNP関係を扱える。それなら，どれを選んでも同じだろうか。第2回の表現力という軸では似ていても，セットアップの条件，証明サイズ，検証と証明生成の負担は異なる。効率性を一つの数字にせず，何を小さくしたいかに分けて考えよう。

群・安全性パラメータを固定し，回路やトレースの規模に対する傾向を整理する。ただし，公開入力の処理コストは別に考慮する。

| 比較する性質 | Groth16 | KZG型PLONK | AIR・FRI型STARK |
| --- | --- | --- | --- |
| 証明サイズ | 3つの群要素 | 定数個の群要素・体要素 | 問い合わせ値・Merkle認証経路等を含み、代表的構成では多重対数的 |
| 検証コスト | 公開入力の処理 + 定数回のペアリング | 公開入力の処理 + 定数個の開示の検証等 | 問い合わせ・認証経路・FRIの検査等。パラメータを固定した代表的構成で多重対数的 |
| セットアップ | 回路固有の鍵とトラステッドセットアップが必要 | 汎用・更新可能なSRS + 回路固有の公開前処理 | 秘密のトラップドアを必要としない |
| ポスト量子安全性 | 大規模な量子計算機に対して安全でない | 大規模な量子計算機に対して安全でない | 適切なハッシュ・パラメータと、量子モデルでの安全性解析が必要 |
| 証明者コストの評価 | QAP処理・群演算等を測定 | 多項式処理・コミットメント等を測定 | トレース処理・低次数拡張・ハッシュ・FRI等を測定 |

STARKのコストはFRIの段階数だけでは決まらず，問い合わせ回数や認証経路にも依存する。証明者の速度は，回路・トレース幅・実装・ハードウェア・メモリ・安全性パラメータで変わるため，上の表から一般的な速度順位を導くことはできない。また，ハッシュを用いるだけで非対話型STARKのポスト量子安全性が自動的に得られるわけではない(第13回4.2節)。

**方式を選ぶ前に，要件を言葉にすることが重要である。** セットアップで誰を信頼できるか，どの安全性が必要か，通信量と計算資源のどちらが制約になるかを整理しよう。演習では，この条件を揃えた実測を使って，選択の理由を説明する。

## 4. 演習:設計判断のシミュレーション

次の場面で，自分が方式を選ぶ立場だと考えてみよう。方式名だけを答えるのではなく，優先する条件，許容する負担，判断に足りない情報まで説明する。

- ブロックチェーン上でオンチェーンの検証コストを極限まで下げたい(ガス代の制約が厳しい)場合
- 新しいアプリケーションを頻繁にリリースする必要があり、その都度トラステッドセットアップをやり直す余裕がない場合
- 量子計算機の実用化を見据えて、長期的な安全性を最優先したい場合
- 証明者側の計算資源が限られており、大規模な計算を効率よく証明したい場合

グループで結論が違ったら，まず前提を比べてみよう。あるグループは検証費用を，別のグループはセットアップや長期安全性を重視しているかもしれない。どの条件を変えると結論が変わるかを確認することが，トレードオフを理解する練習になる。

## まとめと次回予告

今日は，三つの方式を目的・道具・条件から比較した。方式名だけで結論を出さず，どの要求に対する選択かを説明できるようにしよう。

- 完全性/健全性/ゼロ知識性という幕Iの性質を、3プロトコルがそれぞれどう満たしているかを対比した
- 幕IIの道具立てが、プロトコルごとにどう選択的に組み合わされているかを一覧表で整理した
- 幕Iの2軸(表現力・効率性)のうち、効率性の軸の中でも「何を優先するか」という設計思想の違いが、3プロトコルの性能プロファイルの違いを生んでいることを確認した

次回(最終第15回)は，この講義全体の締めくくりとして，再帰的証明(recursive SNARKs)，folding schemes，GKR/sumcheckベースの新潮流を扱う。今日整理した2軸マトリクスに沿って，現在の研究がどの方向を攻めているかを展望する。
