## 本講義の位置づけと到達目標

これまで，目的を定め，必要な道具を揃え，具体的な証明系を読んできた．最終回では，その先に残る課題を考える．長い計算の証明をつなげるには何が必要か．証明を作る側の負担をどう減らせるか．第2回と第14回の「表現力×効率性」を使い，新しい技法がどの問いに答えようとしているかを整理しよう．

到達目標は次の3点:

1. 再帰的証明(recursive SNARKs)がどのような新しい能力をもたらすか，そしてそれがなぜ「効率性の軸」のさらなる拡張と言えるかを理解する
2. Folding schemes(Nova等)が，再帰的証明のどのような実務上の課題を解決しているかを理解する
3. GKR/sumcheckベースの方式が，これまで学んだIOPの枠組み(第10回)とどう関係し，証明者コストを含むどの指標を改善しうるかを，方式ごとの前提とともに理解する

## 1. 再帰的証明(Recursive SNARKs)

### 1.1 発想:証明の中で証明を検証する

証明を検証する処理も，一つの計算である．それなら，検証アルゴリズム $V$ を算術化し，その実行が正しいことを別の証明で示せないだろうか．これが再帰的証明の出発点になる．第4回でプログラムを制約へ翻訳した方法を，今度は検証そのものに適用するのである．

### 1.2 なぜこれが強力なのか

状態遷移が一つ進むたびに，それまでの証明と新しい計算をまとめて証明する．このようにすると，各時点までの**有限の計算履歴**を扱える．証明サイズがステップ数に依存しない構成でも，安全性パラメータや公開状態の大きさへの依存は残る．「無限の計算が完了したことを証明する」という意味ではなく，継続する計算の，いままでの部分を検証可能にするのである．

第11〜13回では個々の計算を証明する構成を学んだ．再帰的証明は，その検証を新たな計算として扱い，証明を合成する技法である．

### 1.3 技術的な要請:検証コストの再帰的な扱いやすさ

検証が通常の計算機で速いとしても，そのまま外側の回路で安く検証できるとは限らない．$V$ が使う群演算やペアリングを，外側の証明系の体でどう表すかが問題になる．異なる体の演算を模倣するコストも含めて，検証の「再帰の中での扱いやすさ」を評価する必要がある．

この問題に取り組む道具の一つが**楕円曲線のサイクル**である．2曲線のサイクルでは，一方の曲線の基礎体が他方のスカラー体に対応し，その逆も成り立つ．この対応は群演算を回路で扱う際に有用で，ペアリングを使わない再帰でも利用される．「ペアリング演算を効率化する曲線ペア」だけを意味せず，すべての再帰的構成が曲線サイクルを必要とするわけでもない．[Nova原論文](https://eprint.iacr.org/2021/370)も参照する．

## 2. Folding Schemes(Nova等)

### 2.1 再帰的証明の実務上の課題

毎ステップで前の証明を完全に検証すると，その検証回路を何度も証明することになる．ここに，繰り返しの負担がある．ペアリングを使う方式ならその演算も重くなりうるが，問題はペアリングの有無だけではない．累積した計算の正しさを，もっと小さな更新作業で引き継げないだろうか．

この繰り返しの負担を軽減する技法が，Nova(Kothapalli, Setty, Tzialla)に代表されるfolding schemesである．Novaは2021年に[ePrintで公開](https://eprint.iacr.org/2021/370)され，CRYPTO 2022で発表された．

### 2.2 基本アイデア:検証すべき関係を「畳み込む」

Novaは，**緩和されたR1CSのインスタンスを集約し，対応するウィットネスを更新する**．前の大きな証明を毎回検証する代わりに，このfoldingの関係を検査する．これをステップ間の連鎖と組み合わせることで，IVC(逐次検証可能計算)を構成する．何を検証し直す代わりに，何を更新しているのかを確認しておこう．

folding単体で簡潔なゼロ知識証明が完成するわけではない．関係を集約するfolding，ステップ間の正しい連鎖を保証するIVC，累積した関係を簡潔な証明にする圧縮は区別する．最終的に提示する証明のサイズ・検証コスト・ゼロ知識性は，組み合わせる構成にも依存する．

第6回のFRIも「折り畳み」という操作を使うが，FRIは低次数近接性を検査するために多項式の次数を縮小し，Novaは制約充足のインスタンスを集約する．段階的な処理という直感は共通していても，同じプロトコルや同じ健全性証明を使うという意味ではない．

Novaを念頭に置いた概念の整理．foldingだけで簡潔なゼロ知識証明が完成するわけではない．FRIの次数縮小とは対象も安全性の議論も異なる．

### 2.3 このアプローチが解決する問題の位置づけ

foldingの利点を測るときは，一回の畳み込みだけを比べないようにしよう．ステップの計算，コミットメント，最後の圧縮も含めて，累積した計算を証明する全体の負担を見る必要がある．圧縮をどの頻度で行うかや実装によっても，得られる改善は変わる．

## 3. GKR/Sumcheckベースの新潮流

### 3.1 Sumcheckプロトコルの復習

第1回で予告したsumcheckに戻ろう．項の数が多い総和について，検証者自身が全項を足す以外の確認方法を考える．対象は，多変数多項式 $g(X_1,\dots,X_n)$ の次の総和である．

$$\sum_{x_1, \dots, x_n \in \{0,1\}} g(x_1, \dots, x_n)$$

という総和の値を，検証者が全項を計算することなく，対話的に(各変数を1つずつ確定させていく形で)検証できるプロトコルである．各変数の次数上限を定め，各ラウンドの一変数多項式の次数と和の整合性を検査する．最後に残るランダム点での $g$ の評価も，検証者自身の計算や別の適切な検証手段で確認する必要がある．この最終確認なしに，総和の正しさは保証できない．SumcheckはIP=PSPACE定理(第1回)の証明技法の中核でもある．

<span id="caption-15-3"></span>

<div class="captioned-table" id="table-15-5" role="group" aria-labelledby="table-caption-15-5">

<p class="table-caption" id="table-caption-15-5"><strong>表 15-5：Sumcheck：総和を，一つの評価の確認まで減らす</strong></p>

| 手順・段階 | 説明 |
| --- | --- |
| 1. 最初の言明 | T = ∑\_&#123;b₁,…,bₙ∈&#123;0,1&#125;&#125; g(b₁,…,bₙ) |
| 2. 一変数の多項式で確認 | p₁(0)+p₁(1)=T → ランダムなr₁でp₁(r₁)へ |
| 3. 変数を一つずつ確定 | 残る和について同じ検査を繰り返す |
| 4. 最後の評価を確認 | g(r₁,…,rₙ)を独立に計算するか，適切な検証手段で確認 |

</div>

各ラウンドで次数上限と和の整合性を検査し，メッセージの後にチャレンジを選ぶ．最後の評価の確認は省けない．GKRでは層ごとの言明の縮約にこの考え方を使う．

### 3.2 GKRプロトコル

GKRは，回路の出力についての言明を，前の層の値についての言明へと移しながら検証する．この移し替えにsumcheckを使う．R1CSやAIRの制約をそのまま検査する方式と比べると，回路の層構造を利用する点に特徴がある．Goldwasser・Kalai・Rothblumの2008年のプロトコルとして，この目的と道具の対応を押さえよう．

### 3.3 GKR/sumcheckを，コスト最適化の一つの方向として読む

大きな回路の証明で，どの作業に時間を使っているだろうか．GKRやsumcheckを使う方式では，層構造や多重線形の表現を利用して，証明者や検証者の仕事を設計できる．ただし，原型のGKRが示した中心的な利点は，回路の深さに応じて検証者の負担を小さくできることにある．これを「GKRなら証明者コストも一般に小さい」と読み替えてはいけない．証明者コストの改善は，回路の形，証明の表現，コミットメントなどを含む具体的な構成と実装に依存する．機械学習の推論を例にすると，どの並列構造を使い，どの作業を証明者と検証者のどちらに負わせるかが問いになる．[GKR原論文の概要](https://www.microsoft.com/en-us/research/publication/delegating-computation-interactive-proofs-muggles/)も，検証者の効率と証明者の多項式時間を分けて述べている．

ただし，すべてのGKR/sumcheck方式がすべてのKZG方式より高速という一般的な順位ではない．SumcheckとKZGは同じ階層の部品でもなく，sumcheckを用いる証明系が多項式コミットメントを併用することもある．回路構造・コミットメント・メモリ使用量・安全性パラメータを揃えて，証明系全体のコストを比較する．[Thalerの教科書](https://people.cs.georgetown.edu/jthaler/ProofsArgsAndZK.html)を併読するとよい．

### 3.4 IOPの枠組みでの位置づけ

元のGKRは対話型証明である．そこから非対話型の暗号学的証明を作るなら，どの情報をコミットし，どのチャレンジをFiat-Shamirで導出するかを設計する．これらはGKRの定義に必ず含まれる部品ではなく，追加する構成である．組み合わせた後の安全性条件まで確認する必要がある．

第10回の「IOP設計 → 実装 → 非対話化」は，このような構成を比較するための見取り図として使える．GKRそのものの定義と，そこから組み立てる非対話型の証明系は区別する．

## 4. 現在の研究地図:2軸マトリクスの拡張

第14回では，効率性を一つの数字で比べられないことを確認した．最終回の技法も，同じように読もう．証明サイズ・検証コスト・証明者コストのどれを改善するのか．合成可能性という機能を加えるのか．セットアップや長期安全性にはどの条件が残るのか．次の表は，新しい技法をこの問いに対応づけるためのものである．

<p class="table-caption" id="table-caption-15-1"><strong>表 15-1：発展的な技術が主に改善する軸</strong></p>

この表を，新しい方式を評価するときの質問表として使ってほしい．証明者コストを下げられても，通信やメモリの負担が増えるかもしれない．簡潔な検証と合成可能性も含め，改善した指標と残った条件を対にして読む．研究全体が一つの目標に移った，という意味ではない．

### 4.1 応用の視点:EthereumのzkEVM {#ethereum-zkevm}

**zkEVMは，EVMの実行が正しいことを証明する仕組み**である．L2のZKロールアップでは，L2で実行した計算の正当性をEthereum L1で検証する．一方，**L1 zkEVM**の研究対象はEthereum本体のブロック実行であり，将来，各検証者の再実行負担を証明検証へ置き換えることを目指す．この二つは区別して読む．ここでの主目的は実行の正当性と検証負担の削減であり，zkEVMという名称だけで取引内容の秘匿を意味するわけではない．[EthereumのL1 zkEVM解説](https://ethereum.org/roadmap/zkevm/)と[ZKロールアップ解説](https://ethereum.org/developers/docs/scaling/zk-rollups/)を参照．

### 4.2 最新動向:速度だけでなく，相互運用性と安全性へ {#_4-2-最新動向-速度だけでなく、相互運用性と安全性へ}

**情報の確認日:2026年9月29日．** 以下は一次資料に基づく研究・提案の状況である．ロードマップ上の目標，EIPの提案，メインネットでの有効化はそれぞれ異なる．EIPの状態は変わりうるため，授業で参照する際は公式ページの最新ステータスも確認する．

- **zkVMを共通基盤にする動き**:EVMの実行プログラムを汎用zkVM上で証明する構成では，ゲストと証明基盤の接続が課題になる．2026年2月16日のzkVM Standards v0は，RV64IM + Zicclsm，プリコンパイルと入出力のCインターフェースを整理した．ゲストの再コンパイル・再リンクは必要であり，「同じバイナリがどこでも動く」という意味ではない．[EFによる標準化の説明](https://zkevm.ethereum.foundation/blog/zkevm-standards-v0-release)
- **高速化と安全性を同時に評価する動き**:平均証明時間だけでなく，証明しにくいブロックへの耐性も重要になる．2026年5月のEF記事は最悪ケースの証明時間への対応を論じ，別の記事は形式検証で保証された範囲と残る前提を検討している．ベンチマークや「形式検証済み」という名称だけで，安全性全体を判断しない．[導入提案と最悪ケースの課題](https://zkevm.ethereum.foundation/blog/eip-8025-optional-execution-proofs-hegota)，[形式検証の範囲に関する検討](https://zkevm.ethereum.foundation/blog/sp1-fv)
- **任意の実行証明から段階的に進める構想**:2026年9月7日のEFの優先事項では，実行証明を任意から将来の必須化へ進める方向が示されている．ただし，ポスト量子対応との工程順序も検討中であり，必須化の導入日が確定したという意味ではない．[EF Protocol: Current and Emerging Priorities](https://blog.ethereum.org/2026/09/07/protocol-priorities)

### 4.3 EIP-8025:Optional Execution Proofs {#eip-8025}

[EIP-8025](https://eips.ethereum.org/EIPS/eip-8025)は，コンセンサス層で**任意の実行証明**を扱う提案で，2026年9月29日に確認した公式ページ上のステータスは**Draft**である．証明者が生成した証明をP2Pで配布し，参加ノードが検証する．現行仕様では**証明は補助チェックであり，ノードは実行ペイロードの再実行を継続する**．証明の必須化や再実行の廃止は，後続EIPで検討する別の段階である．証明生成への報酬もこのEIPでは導入しない．[現行仕様のConsensus Layer節](https://eips.ethereum.org/EIPS/eip-8025#consensus-layer)

2026年5月14日のEF記事はHegotáへの採用を提案しているが，提案の存在をメインネットでの有効化済みという意味に読み替えない．[Hegotáに向けた提案記事](https://zkevm.ethereum.foundation/blog/eip-8025-optional-execution-proofs-hegota)

発問例:「証明が小さくても生成が遅い場合，L2のバッチ処理とL1のブロック検証では何が異なるか」「任意の補助チェックから必須の検証へ移る前に，どのような実測と安全性の根拠が必要か」を議論すると，研究上の効率性と実際の運用要件を結びつけられる．

## まとめ:講義全体の総括

最初に立てた問いから，ここまでの道のりを振り返ろう．目的を先に考えることで，個々の数学やプロトコルを，必要な役割と結び付けて学んできた．

- **幕I**:古典的証明パラダイムの限界から出発し，対話性・ゼロ知識性という目的を，計算量理論と暗号学という2つの動機の合流点として定義した．さらにウィットネスの一般化が要請する質的な転換(算術化の必然性)を理解した
- **幕II**:その目的を実現するための道具(多項式・符号理論・楕円曲線・ペアリング・コミットメント・PCP/IOP)を，単なる数学の羅列としてではなく，暗号学的・計算量理論的な意味づけとともに整備した
- **幕III**:Groth16・PLONK・STARKという具体的なプロトコルを，幕IIの道具がどう組み合わされているかという視点から読み解き，それぞれの設計思想の違いを幕Iの2軸に基づいて対比した．そして最後に，現在の研究がこの2軸のどこを攻めているかを展望した

新しい証明系を読むときも，まず何を実現したい方式なのかを問おう．そのためにどの計算を，どの表現へ変え，何を相手に検査させているのか．そして，どの仮定と計算資源を必要としているのか．この順序で考えれば，知らない方式でも，これまでの道具と結び付けて読み進められる．15回を通じて身につけたいのは，**目的・道具・トレードオフを行き来して，設計の理由を説明する力**である．
