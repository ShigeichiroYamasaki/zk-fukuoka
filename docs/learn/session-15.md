# 第15回(最終回):発展の方向性

## 本講義の位置づけと到達目標

これで幕I〜IIIを通じて、zk-SNARK/zk-STARKの目的・道具・具体的なプロトコルを一通り学んだ。最終回となる今日は、現在進行中の研究の方向性を展望する。ただし新しい話題を無秩序に並べるのではなく、**第2回で導入し、第14回で振り返った「表現力×効率性」の2軸に沿って、現在の研究がどこを攻めているか**という整理された視点で扱う。

到達目標は次の3点:

1. 再帰的証明(recursive SNARKs)がどのような新しい能力をもたらすか、そしてそれがなぜ「効率性の軸」のさらなる拡張と言えるかを理解する
2. Folding schemes(Nova等)が、再帰的証明のどのような実務上の課題を解決しているかを理解する
3. GKR/sumcheckベースの新潮流が、これまで学んだIOPの枠組み(第10回)とどう関係し、証明者コストという新しい最適化軸を切り開いているかを理解する

## 1. 再帰的証明(Recursive SNARKs)

### 1.1 発想:証明の中で証明を検証する

これまで学んだプロトコルは、「ある計算が正しく行われたこと」を証明するものであった。再帰的証明は一歩進んで、**「ある証明が正しく検証されたこと」自体を、別のSNARK/STARKの中で証明する**という発想である。すなわち、検証アルゴリズム $V$ 自体を、算術化(第4回)の対象となる「計算」として扱い、その検証プロセスの正しさを新たな証明で包み込む。

### 1.2 なぜこれが強力なのか

この発想により、複数の証明を1つに集約したり、状態遷移を繰り返す計算について、各時点までの**有限の計算履歴**の正しさを逐次的に証明したりできる。証明サイズをステップ数に依存させない構成もあるが、安全性パラメータや公開状態の大きさへの依存は残る。無限の計算を完了したものとして証明するという意味ではない。

第11〜13回では個々の計算を証明する構成を学んだ。再帰的証明は、その検証を新たな計算として扱い、証明を合成する技法である。

### 1.3 技術的な要請:検証コストの再帰的な扱いやすさ

検証アルゴリズム $V$ を、外側の証明系の算術化で効率よく表現することが重要になる。ペアリングを含む検証ではその演算が重くなりうるほか、群演算を行う体と外側の回路の体が異なる場合にも、変換のコストが生じる。

この問題に取り組む道具の一つが**楕円曲線のサイクル**である。2曲線のサイクルでは、一方の曲線の基礎体が他方のスカラー体に対応し、その逆も成り立つ。この対応は群演算を回路で扱う際に有用で、ペアリングを使わない再帰でも利用される。「ペアリング演算を効率化する曲線ペア」だけを意味せず、すべての再帰的構成が曲線サイクルを必要とするわけでもない。[Nova原論文](https://eprint.iacr.org/2021/370)も参照する。

## 2. Folding Schemes(Nova等)

### 2.1 再帰的証明の実務上の課題

各ステップで前の証明の検証を回路内に組み込む素朴な再帰では、その検証回路が証明者の負担になりうる。ペアリングを検証に用いる方式では、その演算コストも問題になるが、すべての再帰方式がペアリングを使うわけではない。

この繰り返しの負担を軽減する技法が、Nova(Kothapalli, Setty, Tzialla)に代表されるfolding schemesである。Novaは2021年に[ePrintで公開](https://eprint.iacr.org/2021/370)され、CRYPTO 2022で発表された。

### 2.2 基本アイデア:検証すべき関係を「畳み込む」

Novaでは、**緩和されたR1CSのインスタンスを1つに集約し、それに対応するウィットネスも更新する**。これにより、毎回重いSNARK検証を回路内で行う代わりに、軽量なfoldingの検証を使って計算履歴を累積する、IVC(Incrementally Verifiable Computation、逐次検証可能計算)を構成する。

folding単体で簡潔なゼロ知識証明が完成するわけではない。関係を集約するfolding、ステップ間の正しい連鎖を保証するIVC、累積した関係を簡潔な証明にする圧縮は区別する。最終的に提示する証明のサイズ・検証コスト・ゼロ知識性は、組み合わせる構成にも依存する。

第6回のFRIも「折り畳み」という操作を使うが、FRIは低次数近接性を検査するために多項式の次数を縮小し、Novaは制約充足のインスタンスを集約する。段階的な処理という直感は共通していても、同じプロトコルや同じ健全性証明を使うという意味ではない。

### 2.3 このアプローチが解決する問題の位置づけ

Folding schemesは、状態遷移を繰り返すような逐次計算で、累積的な証明のコストを抑えるための技術として位置づけられる。改善の度合いはステップの計算、コミットメント方式、圧縮の頻度や実装によって変わるため、foldingの軽さと最終的な証明生成コストを合わせて評価する。

## 3. GKR/Sumcheckベースの新潮流

### 3.1 Sumcheckプロトコルの復習

第1回で予告したsumcheckプロトコルを、ここで改めて位置づけ直す。Sumcheckプロトコルは、多変数多項式 $g(X_1, \dots, X_n)$ に対して、

$$\sum_{x_1, \dots, x_n \in \{0,1\}} g(x_1, \dots, x_n)$$

という総和の値を、検証者が全項を計算することなく、対話的に(各変数を1つずつ確定させていく形で)検証できるプロトコルである。各変数の次数上限を定め、各ラウンドの一変数多項式の次数と和の整合性を検査する。最後に残るランダム点での $g$ の評価も、検証者自身の計算や別の適切な検証手段で確認する必要がある。この最終確認なしに、総和の正しさは保証できない。SumcheckはIP=PSPACE定理(第1回)の証明技法の中核でもある。

### 3.2 GKRプロトコル

GKR(Goldwasser-Kalai-Rothblum, 2008)は、sumcheckプロトコルを、回路の各層ごとに適用することで、回路計算の正しさを検証する対話型証明を構成する技法である。第4回で学んだR1CS/AIRとは異なる算術化・検証の系統として位置づけられる。

### 3.3 なぜ近年再評価されているのか

GKR/sumcheckベースの手法は、回路の層構造や多重線形多項式の表現を利用して、証明者コストを抑える設計につながる。大規模な回路や機械学習の推論を例に、「どの構造を利用すれば、証明者の処理を減らせるか」を考えることができる。

ただし、すべてのGKR/sumcheck方式がすべてのKZG方式より高速という一般的な順位ではない。SumcheckとKZGは同じ階層の部品でもなく、sumcheckを用いる証明系が多項式コミットメントを併用することもある。回路構造・コミットメント・メモリ使用量・安全性パラメータを揃えて、証明系全体のコストを比較する。[Thalerの教科書](https://people.cs.georgetown.edu/jthaler/ProofsArgsAndZK.html)を併読するとよい。

### 3.4 IOPの枠組みでの位置づけ

元のGKRは対話型証明であり、多項式コミットメントやFiat-Shamirを必須の構成要素として含むわけではない。非対話型の暗号学的証明にする際には、必要な多項式評価をコミットメントで認証し、Fiat-Shamirでチャレンジを導出するなどの設計を考えられる。その場合は、各構成要素と変換の安全性条件を確認する。

第10回の「IOP設計 → 実装 → 非対話化」は、このような構成を比較するための見取り図として使える。GKRそのものの定義と、そこから組み立てる非対話型の証明系は区別する。

## 4. 現在の研究地図:2軸マトリクスの拡張

第2回・第14回で使ってきた2軸マトリクスを、最後にもう一段階拡張してみよう。「効率性」の軸は、実は単一の軸ではなく、**証明サイズ・検証コスト・証明者コスト・セットアップの柔軟性・長期安全性**という複数の下位軸に分解できることが、幕III全体を通じて明らかになった。本講義で扱った技法は、この多次元の設計空間の中で、合成可能性や証明者コストなどを改善する方向として整理できる。安全性やセットアップの前提は、性能と並べて確認する設計条件でもある。

| 技術            | 主に改善する軸                     |
| --------------- | ---------------------------------- |
| 再帰的証明      | 証明の合成可能性(新しい能力の追加) |
| Folding schemes | 証明者コスト(特に逐次計算)         |
| GKR/sumcheck    | 証明者コスト(特に大規模並列計算)   |

この表は、**簡潔な検証に加えて、証明者コストや合成可能性を改善する研究の方向**を示している。研究全体を単一の軸への移行として捉えるのではなく、どの指標を改善し、どの条件やコストが残るかを読むために使う。

### 4.1 応用の視点:EthereumのzkEVM {#ethereum-zkevm}

**zkEVMは、EVMの実行が正しいことを証明する仕組み**である。L2のZKロールアップでは、L2で実行した計算の正当性をEthereum L1で検証する。一方、**L1 zkEVM**の研究対象はEthereum本体のブロック実行であり、将来、各検証者の再実行負担を証明検証へ置き換えることを目指す。この二つは区別して読む。ここでの主目的は実行の正当性と検証負担の削減であり、zkEVMという名称だけで取引内容の秘匿を意味するわけではない。[EthereumのL1 zkEVM解説](https://ethereum.org/roadmap/zkevm/)と[ZKロールアップ解説](https://ethereum.org/developers/docs/scaling/zk-rollups/)を参照。

### 4.2 最新動向:速度だけでなく、相互運用性と安全性へ

**情報の確認日:2026年9月27日。** 以下は一次資料に基づく研究・提案の状況である。ロードマップ上の目標、EIPの提案、メインネットでの有効化はそれぞれ異なる。

- **zkVMを共通基盤にする動き**:EVMの実行プログラムを汎用zkVM上で証明する構成では、ゲストと証明基盤の接続が課題になる。2026年2月16日のzkVM Standards v0は、RV64IM + Zicclsm、プリコンパイルと入出力のCインターフェースを整理した。ゲストの再コンパイル・再リンクは必要であり、「同じバイナリがどこでも動く」という意味ではない。[EFによる標準化の説明](https://zkevm.ethereum.foundation/blog/zkevm-standards-v0-release)
- **高速化と安全性を同時に評価する動き**:平均証明時間だけでなく、証明しにくいブロックへの耐性も重要になる。2026年5月のEF記事は最悪ケースの証明時間への対応を論じ、別の記事は形式検証で保証された範囲と残る前提を検討している。ベンチマークや「形式検証済み」という名称だけで、安全性全体を判断しない。[導入提案と最悪ケースの課題](https://zkevm.ethereum.foundation/blog/eip-8025-optional-execution-proofs-hegota)、[形式検証の範囲に関する検討](https://zkevm.ethereum.foundation/blog/sp1-fv)
- **任意の実行証明から段階的に進める構想**:2026年9月7日のEFの優先事項では、実行証明を任意から将来の必須化へ進める方向が示されている。ただし、ポスト量子対応との工程順序も検討中であり、必須化の導入日が確定したという意味ではない。[EF Protocol: Current and Emerging Priorities](https://blog.ethereum.org/2026/09/07/protocol-priorities)

### 4.3 EIP-8025:Optional Execution Proofs {#eip-8025}

[EIP-8025](https://eips.ethereum.org/EIPS/eip-8025)は、コンセンサス層で**任意の実行証明**を扱う提案で、確認時点のステータスは**Draft**である。証明者が生成した証明をP2Pで配布し、参加ノードが検証する。現行仕様では**証明は補助チェックであり、ノードは実行ペイロードの再実行を継続する**。証明の必須化や再実行の廃止は、後続EIPで検討する別の段階である。証明生成への報酬もこのEIPでは導入しない。[現行仕様のConsensus Layer節](https://eips.ethereum.org/EIPS/eip-8025#consensus-layer)

2026年5月14日のEF記事はHegotáへの採用を提案しているが、提案の存在をメインネットでの有効化済みという意味に読み替えない。[Hegotáに向けた提案記事](https://zkevm.ethereum.foundation/blog/eip-8025-optional-execution-proofs-hegota)

### 4.4 講義の研究地図に位置づける

次の表は、これらの動向を本講義の観点から整理したものである。EIP-8025が特定のfolding schemeやGKRを採用すると主張するものではない。

| 応用での問い | 本講義との接続 | 評価する軸 |
| --- | --- | --- |
| EVMの実行規則を漏れなく証明できるか | 算術化(第4回)と一般の計算の表現 | 表現力・互換性・実装の正しさ |
| 証明を必要な時間内に生成できるか | GKR/sumcheck、並列化、証明者コスト | 平均・最悪ケースの遅延、メモリ・機材コスト |
| 分割した計算の証明を扱いやすくまとめられるか | 再帰的証明・集約。foldingは構成に応じた選択肢 | 証明サイズ・生成コスト・通信量 |
| 検証負担を下げつつ安全に移行できるか | 健全性(第1・14回)と段階的なプロトコル導入 | 検証コスト・安全性・運用上の信頼性 |

発問例:「証明が小さくても生成が遅い場合、L2のバッチ処理とL1のブロック検証では何が異なるか」「任意の補助チェックから必須の検証へ移る前に、どのような実測と安全性の根拠が必要か」を議論すると、研究上の効率性と実際の運用要件を結びつけられる。

## まとめ:講義全体の総括

15回を通じて、次のような道のりを辿ってきた:

- **幕I**:古典的証明パラダイムの限界から出発し、対話性・ゼロ知識性という目的を、計算量理論と暗号学という2つの動機の合流点として定義した。さらにウィットネスの一般化が要請する質的な転換(算術化の必然性)を理解した
- **幕II**:その目的を実現するための道具(多項式・符号理論・楕円曲線・ペアリング・コミットメント・PCP/IOP)を、単なる数学の羅列としてではなく、暗号学的・計算量理論的な意味づけとともに整備した
- **幕III**:Groth16・PLONK・STARKという具体的なプロトコルを、幕IIの道具がどう組み合わされているかという視点から読み解き、それぞれの設計思想の違いを幕Iの2軸に基づいて対比した。そして最後に、現在の研究がこの2軸のどこを攻めているかを展望した

この講義を通じて得てほしいのは、個々のプロトコルの詳細な記憶ではなく、**「なぜこの技術がこの形をしているのか」を、目的・道具・トレードオフという一貫した枠組みで問い続ける姿勢**である。この分野は現在も急速に発展しているが、今日学んだ2軸マトリクスという地図があれば、新しい技術が登場した際にも、それがどこを改善しようとしているのかを自分自身で位置づけられるはずである。
