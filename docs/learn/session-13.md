# 第13回:STARK

[各回の授業](./sessions) · [トピック別](./topics) · [シラバスの第13回](./#session-13) · [演習](../exercises/)

## 本講義の位置づけと到達目標

前回までに学んだGroth16とKZG型PLONKは、いずれもペアリングとトラステッドセットアップを用いる。ただし、Groth16はQAPとペアリングによる直接的な構成であり、KZGを部品として用いるPLONKとは異なる。今日扱うSTARK(Scalable Transparent ARgument of Knowledge; Ben-Sasson et al., 2018)は、**トラステッドセットアップそのものを排除する**という設計目標を出発点とし、第5・6回で整備した符号理論的な道具(RS符号、FRI)を全面的に活用して構成される。

到達目標は次の3点:

1. 透明性という設計目標のもとで、AIRとFRIを組み合わせる代表的なSTARK構成を理解する
2. STARKの全体構成を、第10回の3段階の見取り図に沿って理解する
3. 透明性とその他の性質(証明サイズ、検証コスト、ポスト量子安全性)とのトレードオフを評価できるようになる

---

## 1. 透明性(Transparency)という設計目標

### 1.1 トラステッドセットアップへの不安

第11回・第12回で見たように、Groth16・KZG型PLONKはいずれもトラステッドセットアップ(SRS生成時の秘密のトラップドア)に依存していた。この秘密が万が一漏洩すれば、健全性そのものが崩れる。マルチパーティ計算による分散生成(第11回で触れた)はこのリスクを軽減するが、根本的には「誰も秘密を知らない」ことを完全な確証をもって検証することはできない、という本質的な不安が残る。

### 1.2 透明性の定義

**透明性(transparency)**とは、セットアップで秘密のトラップドアを生成・保持・破棄する必要がない性質を指す。パラメータは公開の手順で定め、必要なランダム性も公開に生成できる。すべてのパラメータが乱数である必要はない。

本講義では、AIR・FRI・Merkle木を組み合わせる代表的なSTARKを扱う。Merkle木は評価値の表への拘束性を、FRIは低次数多項式への近接性の検査を担う。この構成はKZGのような秘密のトラップドアを必要としない。ただし、透明性だけからAIR・FRIが唯一の選択として決まるわけではない。また、証明系全体の安全性はハッシュの衝突耐性だけでは説明できず、4.2節の条件も必要になる。

---

## 2. AIRによる算術化の再確認

### 2.1 なぜAIRが選ばれるのか

第4回で学んだように、AIR(Algebraic Intermediate Representation)は計算の実行トレースを出発点とする算術化技法であった。STARKがAIRを採用する理由は、透明性そのものというより、**FRIとの相性の良さ**にある。AIRは計算の各ステップを行として並べたトレーステーブルを多項式として符号化するが、この符号化は本質的に「評価点表現された多項式」であり、これは第5〜6回で整備したRS符号・FRIの対象そのものと自然に一致する。

### 2.2 遷移制約・境界制約の復習と拡張

遷移制約は指定されたステップ間の関係を、境界制約は初期値や出力などの公開条件を表す。制約多項式が、それぞれの適用点で0になることを、その点集合の消失多項式による割り切れ性として表現する。

これらの商に対する次数上限を定め、ランダムな係数でまとめて合成多項式を構成する。係数は、対象のトレースをコミットした後で決める必要がある。複数の不正な制約が偶然打ち消し合う確率を抑える考え方は、第3回の確率的多項式検査につながる。合成多項式の低次数性だけでなく、元のトレースから正しく構成されていることも検査する。

## 3. STARKの全体構成

### 3.1 概略のステップ

代表的な非対話型のAIR・FRI構成は、次の流れで理解できる。細部は方式によって異なるが、コミットしてから対応するチャレンジを導出する順序が重要である:

1. 証明者が計算を実行し、実行トレースを生成する。境界制約には初期状態・出力等の公開条件を含める
2. トレースの各列を補間し、より大きな評価領域へ低次数拡張する。その評価表をMerkle木でコミットする
3. それまでのトランスクリプトとコミットメントから、Fiat-Shamirによって制約をまとめる係数を導出する
4. 遷移制約・境界制約の消失多項式に対する商を用いて合成多項式を構成し、その評価表にコミットする
5. FRIの各段階でも、評価表へのコミットメントに続いて折り畳みのチャレンジを導出し、次数の上限を段階的に下げる
6. その後に導出した問い合わせ点について、トレース・合成多項式・FRIの表の必要な評価値とMerkle認証経路を開示する
7. 検証者は認証経路、トレースと合成多項式の関係、FRIの折り畳みと最終条件を確認する

**FRIだけで計算の正しさが分かるわけではない。** 低次数近接性、制約の割り切れ性、表どうしの整合性、公開入力への結び付けを合わせて検証する。[STARK原論文](https://eprint.iacr.org/2018/046)を参照。

ゼロ知識性を持たせる構成では、開示するトレース評価値等からウィットネスの情報が漏れないよう、次数上限や制約と整合するランダムなマスキングも必要になる。透明性やFRIの使用だけで、ゼロ知識性が自動的に得られるわけではない。

### 3.2 検証コストと証明サイズ

証明には、FRIの各段階の情報だけでなく、問い合わせた評価値やMerkle認証経路も含まれる。そのため、証明サイズと検証コストをFRIの段階数だけから単純な対数比例とすることはできない。

固定した安全性・符号パラメータのもとでは、代表的な構成はトレース長に対して多重対数的な証明サイズ・検証コストを目指す。具体的な値は、問い合わせ回数、ハッシュ長、折り畳み方式、集約・圧縮の有無等に依存する。公開入力の読み取り等のコストも別途考慮する。KB単位の数値を比較する際は、回路・入力・実装・安全性パラメータを明示する。

## 4. 透明性とその他の性質のトレードオフ

### 4.1 証明サイズ・検証コストのトレードオフ

Groth16や原論文のKZG型PLONKは、固定した群と安全性パラメータのもとで、回路サイズによらない定数個の群要素等からなる証明を実現する。ただし公開入力の処理は必要であり、検証全体が公開入力数によらず定数時間になるわけではない。

一方、ここで扱うFRI型STARKはトラステッドセットアップを不要にする代わりに、評価値や認証経路の通信・検証を必要とする。**比較すべきなのは、特定の構成と条件におけるセットアップ・証明サイズ・検証コストの組合せ**である。「透明な証明は必ず大きくなる」という不可能性定理ではなく、Groth16をKZG系と分類することも正確ではない。

### 4.2 ポスト量子安全性

楕円曲線上の離散対数はShorの量子アルゴリズムで効率的に解けるため、その困難性を必要とするGroth16やKZG型PLONKは、大規模な誤り訂正量子計算機に対する安全性を持たない。ハッシュベースのSTARKはこの代数的前提を避けられる点で、ポスト量子安全性を目指す有力な構成である。

ただし、Merkle木の拘束性に必要なハッシュの衝突耐性と、非対話型証明全体の安全性は区別する。後者には、FRI等の健全性誤差の解析とFiat-Shamir変換の安全性も必要になる。量子攻撃者に対しては、量子ランダムオラクルモデルでの解析、ハッシュ長や安全性パラメータ、具体的構成に対する定理の適用条件を確認する。**ハッシュを使うだけでポスト量子安全性が保証されるわけではない。**

[Fiat-Shamir変換の量子モデルでの安全性に関する研究](https://arxiv.org/abs/1902.07556)は、この区別を学ぶための文献である。そこでの定理を、条件の確認なしに任意の多ラウンドSTARKへ適用してはならない。

### 4.3 証明者の計算コスト

固定したトレース幅・制約次数・安全性パラメータのもとでは、STARKはAIRベースの算術化とFFT的な多項式演算(NTT、[第3回](./session-03)で触れた乗法群の構造がここで実務上重要になる)を活用することで、証明者側の計算量もトレース長 $n$ に対して準線形($O(n \log n)$ 程度)に抑えられる設計になっていることが多い。ただし、制約評価やハッシュ処理、メモリ使用量、ハードウェアも実時間を左右する。R1CS/QAP系を含む他方式より常に速いという意味ではなく、同じ計算と安全性条件で比較する必要がある。

## 5. 第10回の見取り図に沿った振り返り

- **IOP設計**:AIRの制約を商多項式で表し、ランダムな集約とFRIによる低次数近接性検査を、トレースとの整合性検査と組み合わせる
- **実装**:Merkle木でオラクルの評価表にコミットし、問い合わせ値を認証する。FRIは低次数近接性を担い、Merkle木の拘束性とは別の役割を果たす
- **非対話化**:コミットメントとトランスクリプトを結び付けたFiat-Shamir変換(第9回)を用い、その安全性モデルを明示する

この3段階の構成は、前回のPLONKと基本的な骨格(IOP設計→実装→非対話化)は共通しているが、**「実装」段階での技法選択(ペアリング+KZG vs ハッシュ+FRI)が根本的に異なる**、という点を改めて強調しておきたい。この選択は透明性・証明サイズ・ポスト量子安全性に大きく影響するが、算術化・パラメータ・実装も性能と安全性に関わる。

## まとめと次回予告

今日学んだこと:

- 透明性を実現する代表例として、AIR・FRI・Merkle木を組み合わせる構成を学んだこと
- AIRがFRIとの相性の良さから選ばれていること、遷移制約・境界制約の構成
- コミットしてからチャレンジを導出する順序と、制約・低次数近接性・表の整合性を合わせて検証する必要性を確認した
- 透明性・証明サイズ・検証コスト・ポスト量子安全性・証明者の計算コストという複数の軸でのトレードオフ

次回(第14回)は、幕III全体の統合回として、Groth16・PLONK・STARKの3つを、幕Iで定義した完全性(completeness)・健全性(soundness)・ゼロ知識性(zero-knowledge)という性質、および幕IIで導入した暗号学的仮定・計算量理論的結果がそれぞれどこで効いているかを、一覧化しながら横断的に振り返る。

## 講義中に使える発問例

- 「トラステッドセットアップに一切頼らずにプロトコルを構成するには、どのような制約が課されるか」を、KZGの構造(第8回)を思い出させながら議論させると、FRIを選ぶ動機が見えやすい
- 第8回の比較表を再度提示し、「STARKが失うものと得るものは何か」を学生自身にまとめさせる
- 「なぜ楕円曲線ベースの仮定は量子計算機に弱く、ハッシュ関数は(現時点で)そうではないと考えられているのか」を、Shorのアルゴリズムの直感(周期発見)に軽く触れながら議論させると発展的な理解につながる
