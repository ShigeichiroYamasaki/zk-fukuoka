# 第9回:Fiat-Shamir変換とROMの功罪

**著者名：山崎重一郎**<br>

最終更新日付：2026年9月28日

## 本講義の位置づけと到達目標

これまで，検証者が途中でランダムな質問を出す手続きを見てきた．しかし，証明を一度作り，後から別の人にも検証してもらいたい場合，毎回の対話は負担になる．今日は，この質問をどう置き換えるかを考える．Fiat-Shamir変換の手順と，その安全性を示すモデルを分けて理解することが目標である．なお，KZGの評価開示それ自体は，評価点が与えられれば非対話的に行える．

到達目標は次の3点:

1. Fiat-Shamir変換の仕組みを理解し，対話型プロトコルがどのように非対話型に変換されるかを把握する
2. Random Oracle Model(ROM)における安全性証明の考え方を理解する
3. ROMは明確に定義された理想モデルである一方，具体的なハッシュへの置換はヒューリスティックであり，その一般的な正当化には反例があることを知り，その意義と限界を批判的に評価できるようになる

---

## 1. なぜ非対話性が必要か

### 1.1 実務上の要請

ブロックチェーンに証明を載せる場面を考えよう．検証する全員と個別にやり取りするより，公開された証明をそれぞれが検査できる方が扱いやすい．証明者が後から応答する必要もなくなる．この運用上の目的が，非対話性を求める理由である．

### 1.2 これまでのプロトコルの共通構造

Schnorrでは，コミット・チャレンジ・応答という3段階を見た．FRIでも，表を固定した後でランダムなチャレンジを与える．ただしFRI全体は多段階のIOPであり，そのまま3手のΣ-protocolと呼ぶわけではない．共通するのは，公開コイン型のやり取りで，先のメッセージに対してランダムなチャレンジを与える点である．

---

## 2. Fiat-Shamir変換

### 2.1 基本アイデア

検証者がその場で乱数を選ぶ代わりに，誰でも同じ値を再計算できる規則を使えないだろうか．Fiat-Shamir変換では，すでに固定した情報をハッシュ関数へ入力し，チャレンジを得る．考え方は次のとおりである．

> 検証者が送るランダムなチャレンジを，証明者自身が「それまでの対話の書き起こし(transcript)にハッシュ関数を適用した値」で代用する

具体的には，Σ-protocol型のプロトコルにおいて，チャレンジ $c$ を検証者から受け取る代わりに，証明者自身が

$$c = H(\text{コミット}, x)$$

この式でハッシュを計算するのは証明者だけではない．検証者も同じ入力からチャレンジを再計算し，応答を検査する．実際の構成では，言明・公開パラメータ・それまでのメッセージ・プロトコルの識別情報などを曖昧さなく符号化する．何をハッシュに含めるかも，方式の一部である．

### 2.2 なぜこれで安全なのか(直感)

証明者はコミットを選び，ハッシュ値を調べることができる．したがって，「都合のよい値を探すこと自体ができない」という説明は正確ではない．必要なのは，効率的な相手が試行を繰り返しても，不正な証明を作る確率を十分小さく抑えられることである．ハッシュの一方向性だけではこの結論は得られない．次のROMで，問い合わせと成功確率を明示して解析する．

## 3. Random Oracle Model(ROM)

### 3.1 モデルの定義

どの入力への応答が，どのように決まるのかを数学的に扱うため，ハッシュを理想的なランダム関数として考える．これがRandom Oracle Modelである．ランダムといっても，問い合わせるたびに同じ入力の答えが変わるわけではない．次の三つを同時に満たす．

- $H$ への問い合わせに対して，まだ問い合わせたことのない入力には一様ランダムな出力を返す
- 同じ入力には常に同じ出力を返す(一貫性)
- 攻撃者を含むすべてのアルゴリズムは，$H$ の中身を直接見ることはできず，問い合わせを通じてのみアクセスできる

<StudyDiagram id="09-2" />

### 3.2 ROMでの安全性証明の骨格

Schnorr型の構成など，必要な条件を満たす場合には，第6回のforking lemmaが使える．同じ敵対者の実行を分岐させ，あるオラクル応答を変えて，異なるチャレンジに対する受理記録を得る．その記録からウィットネスを抽出する方針である．ただし，すべての公開コイン型プロトコルに同じ証明が適用できるわけではない．変換前の性質と，変換後に示したい性質を確認する必要がある．

---

## 4. ROMの限界

### 4.1 ROMから実装への置換はヒューリスティックである {#_4-1-romはあくまでヒューリスティックである}

ROMで安全性を示したとき，何について証明できたのかを確認しよう．証明の対象は，理想的なランダムオラクルを使う方式である．実装ではSHA-256などの具体的な関数を使う．この置き換えによって，同じ保証が自動的に引き継がれるわけではない．モデルの中の定理と，モデルを実装に適用する判断を分ける必要がある．

### 4.2 理論的な反例

Canetti・Goldreich・Haleviの結果は，この区別が言葉だけの問題ではないことを示す．ROMでは安全でも，具体的なハッシュ関数で実体化すると安全でなくなる人工的な構成がある．2004年のJACM論文は，このような反例を扱っている．これは実用方式への攻撃を一括して示す結果ではなく，ROMから実装への保証を一般には導けないという結果である．

<StudyDiagram id="09-3" />

### 4.3 それでもROMが広く使われる理由

では，反例があるならROMで解析する意味はないのだろうか．理想化した条件のもとで，攻撃者の問い合わせを含めて方式を調べられることには意味がある．一方で，得られた証明の範囲を超えて安全性を主張してはいけない．実用上の理由を，この区別を保ちながら整理しよう．

- CGHのような反例は，意図的に病的な構成として作られたものであり，実際に使われるプロトコル(Fiat-Shamir変換によるSchnorr署名など)に対する具体的な攻撃が見つかっているわけではない
- ROMでの証明は，明示した仮定と攻撃モデルのもとで対象の安全性を保証する．実装上の欠陥やモデル外の攻撃まで除外したことにはならない
- ROMを使わない構成との効率比較は，要求する機能とセットアップモデルに依存する．第11回のGroth16はCRSモデルで直接構成され，Fiat-ShamirやROMを必要としない

### 4.4 この批判的視点をどう位置づけるか

方式を読むときは，どこでランダムオラクルを使い，その仮定から何を示しているかを追おう．「安全性証明がある」という一言で済ませず，モデル・前提・実装を分けて確認する．この読み方は，後のPLONKやSTARKを評価する際にも使う．

## まとめと次回予告

今日は，対話をなくす変換と，その変換の安全性を扱うモデルを学んだ．手順，モデル，実装の三つを分けて振り返ろう．

- Fiat-Shamir変換:対話型プロトコルのチャレンジをハッシュ関数で代用することによる非対話化の仕組み
- Random Oracle Model:ハッシュ関数を理想化したモデルにおける安全性証明の考え方，forking lemma(第6回)がここで実際に使われること
- ROMの理論的な限界:CGHの反例が示す，ROMでの証明が万能の保証にならないことの理論的根拠
- それでもROMが実務で広く受け入れられている理由と，その批判的な評価の必要性

次回(第10回)は幕IIの最終回として，PCP定理とIOPの枠組みを扱う．これまで断片的に触れてきた計算量理論的な背景(IP=PSPACE，Cook-Levin定理)を，PCP定理という形で総括し，近似困難性研究とのつながりにも触れる．これにより，幕IIで整備したすべての道具が，幕IIIで実際のプロトコルを読むための準備として揃うことになる．

## 講義中に使える発問例

- Fiat-Shamir変換の説明前に，「検証者を対話に参加させずにランダム性を確保するには，どんな方法が考えられるか」を自由に考えさせると，ハッシュ関数を使う発想の必然性が見えやすい
- CGHの反例を紹介する際，「数学的に証明されていることと，実際に安全であることの違いは何か」を議論させると，批判的思考の訓練になる
- 「ROMに依拠しない，より厳密な安全性証明を目指すべきか，それとも実用性を優先すべきか」という設計哲学上の対立軸について，学生同士で意見交換させるのも効果的
