# 第9回:Fiat-Shamir変換とROMの功罪

## 本講義の位置づけと到達目標

これまで，検証者が途中でランダムな質問を出す手続きを見てきた．しかし，証明を一度作り，後から別の人にも検証してもらいたい場合，毎回の対話は負担になる．今日は，この質問をどう置き換えるかを考える．Fiat-Shamir変換の手順と，その安全性を示すモデルを分けて理解することが目標である．なお，KZGの評価開示それ自体は，評価点が与えられれば非対話的に行える．

到達目標は次の3点:

1. Fiat-Shamir変換の仕組みを理解し，対話型プロトコルがどのように非対話型に変換されるかを把握する
2. Random Oracle Model(ROM)における安全性証明の考え方を理解する
3. ROMは明確に定義された理想モデルである一方，具体的なハッシュへの置換はヒューリスティックであり，その一般的な正当化には反例があることを知り，その意義と限界を批判的に評価できるようになる


::: tip 前提知識とこの回の論点
対話型証明でのチャレンジ（[第2回](./session-02)），巻き戻しと健全性増幅（[第6回](./session-06)），コミットメント（[第8回](./session-08)）を思い出す．ROMを読む際は，[暗号学の安全性チュートリアル](./cryptographic-security-tutorial)の確率的な相手・安全性実験の考え方も役立つ．

順序は「対話をなくす必要→Fiat–Shamirがチャレンジを導く方法→ROMでの証明→理想モデルを実ハッシュに置き換える限界」と進む．変換の手順と，その安全性を証明するモデルを混同しない．
:::

## 1. なぜ非対話性が必要か

### 1.1 実務上の要請

ブロックチェーンに証明を載せる場面を考えよう．検証する全員と個別にやり取りするより，公開された証明をそれぞれが検査できる方が扱いやすい．証明者が後から応答する必要もなくなる．この運用上の目的が，非対話性を求める理由である．

### 1.2 これまでのプロトコルの共通構造

Schnorrでは，コミット・チャレンジ・応答という3段階を見た．FRIでも，表を固定した後でランダムなチャレンジを与える．ただしFRI全体は多段階のIOPであり，そのまま3手のΣ-protocolと呼ぶわけではない．共通するのは，公開コイン型のやり取りで，先のメッセージに対してランダムなチャレンジを与える点である．

## 2. Fiat-Shamir変換

### 2.1 基本アイデア

検証者がその場で乱数を選ぶ代わりに，誰でも同じ値を再計算できる規則を使えないだろうか．Fiat-Shamir変換では，すでに固定した情報をハッシュ関数へ入力し，チャレンジを得る．考え方は次のとおりである．

> 検証者が送るランダムなチャレンジを，証明者自身が「それまでの対話の書き起こし(transcript)にハッシュ関数を適用した値」で代用する

具体的には，Σ-protocol型のプロトコルにおいて，チャレンジ $c$ を検証者から受け取る代わりに，証明者自身が

$$c = H(\text{コミット}, x)$$

この式でハッシュを計算するのは証明者だけではない．検証者も同じ入力からチャレンジを再計算し，応答を検査する．実際の構成では，検証対象の命題・公開パラメータ・それまでのメッセージ・プロトコルの識別情報などを曖昧さなく符号化する．何をハッシュに含めるかも，方式の一部である．

### 2.2 なぜこれで安全なのか(直感)

証明者はコミットを選び，ハッシュ値を調べることができる．したがって，「都合のよい値を探すこと自体ができない」という説明は正確ではない．必要なのは，効率的な相手が試行を繰り返しても，不正な証明を作る確率を十分小さく抑えられることである．ハッシュの一方向性だけではこの結論は得られない．次のROMで，問い合わせと成功確率を明示して解析する．

概念の整理．実装では公開入力・プロトコル識別子・それまでの記録などを曖昧さなく符号化する．ハッシュの一方向性だけで変換の安全性が証明されるわけではない．

### 2.3 ハッシュ値を有限体のチャレンジに変換する

実装ではハッシュ出力を，プロトコルが使う有限体 $\mathbb F_p$ の元へ変換する必要がある．ハッシュから一様な $k$ ビット整数 $u$ を作り，単純に $u\bmod p$ とすると，$2^k$ が $p$ で割り切れない場合に剰余の出現回数が揃わない．例えば3ビット値を法7にすると，剰余0と1は各2通り，残りは各1通りであり，一様ではない．

小さな教材実装では，$p$ 以上の候補を捨て，ハッシュのカウンタを進めて次の候補を生成する棄却法で偏りを避けられる．実際のプロトコルでは，仕様で定めたhash-to-fieldまたは一様性を解析したreductionを使い，ハッシュ入力にはプロトコル識別子・ラウンド・公開入力・先行トランスクリプトを曖昧さなく含める．独自の変換を安易に設計せず，採用した方式の仕様と実装を確認しよう．

原論文のPLONKは対話型の多項式検査をFiat–Shamirで非対話化する．証明者が先にコミットしたワイヤ多項式などを含むトランスクリプトから，置換引数の $\beta,\gamma$ などのチャレンジを導く．コミットより前にチャレンジを選べるなら証明者が値を合わせられるため，順序とトランスクリプトへの束縛が重要である．この変換の安全性は単なるハッシュの一方向性ではなく，ROMなどのモデルと仮定のもとで評価する．[第12回](./session-12)の検査順序と併せて確認しよう．

## 3. Random Oracle Model(ROM)

### 3.1 モデルの定義

どの入力への応答が，どのように決まるのかを数学的に扱うため，ハッシュを理想的なランダム関数として考える．これがRandom Oracle Modelである．ランダムといっても，問い合わせるたびに同じ入力の答えが変わるわけではない．次の三つを同時に満たす．

- $H$ への問い合わせに対して，まだ問い合わせたことのない入力には一様ランダムな出力を返す
- 同じ入力には常に同じ出力を返す(一貫性)
- 攻撃者を含むすべてのアルゴリズムは，$H$ の中身を直接見ることはできず，問い合わせを通じてのみアクセスできる

小さな出力の説明例．実際の安全性解析では十分な出力長と問い合わせ回数を考える．異なる入力に同じ出力が出る可能性もある．

### 3.2 ROMでの安全性証明の骨格

Schnorr型の構成など，必要な条件を満たす場合には，第6回のforking lemmaが使える．同じ敵対者の実行を分岐させ，あるオラクル応答を変えて，異なるチャレンジに対する受理記録を得る．その記録からウィットネスを抽出する方針である．ただし，すべての公開コイン型プロトコルに同じ証明が適用できるわけではない．変換前の性質と，変換後に示したい性質を確認する必要がある．

## 4. ROMの限界

### 4.1 ROMから実装への置換はヒューリスティックである {#_4-1-romはあくまでヒューリスティックである}

ROMで安全性を示したとき，何について証明できたのかを確認しよう．証明の対象は，理想的なランダムオラクルを使う方式である．実装ではSHA-256などの具体的な関数を使う．この置き換えによって，同じ保証が自動的に引き継がれるわけではない．モデルの中の定理と，モデルを実装に適用する判断を分ける必要がある．

### 4.2 理論的な反例

Canetti・Goldreich・Haleviの結果は，この区別が言葉だけの問題ではないことを示す．ROMでは安全でも，具体的なハッシュ関数で実体化すると安全でなくなる人工的な構成がある．2004年のJACM論文は，このような反例を扱っている．これは実用方式への攻撃を一括して示す結果ではなく，ROMから実装への保証を一般には導けないという結果である．

<p class="table-caption" id="table-caption-09-3"><strong>表 09-3：理想モデルでの証明と，実装の安全性を区別する</strong></p>

| 項目 | 説明 |

| ROMでの命題 | Hを理想的なランダムオラクルとして扱い，安全性を証明する． |

ROMの証明だけでは，任意の具体的ハッシュへの置き換えを保証しない

CGHの反例は，この置き換えをすべての構成について正当化できないことを示す．ここから，実用のFiat–Shamir構成がすべて破られるとはいえない．

### 4.3 それでもROMが広く使われる理由

では，反例があるならROMで解析する意味はないのだろうか．理想化した条件のもとで，攻撃者の問い合わせを含めて方式を調べられることには意味がある．一方で，得られた証明の範囲を超えて安全性を主張してはいけない．実用上の理由を，この区別を保ちながら整理しよう．

- CGHのような反例は，意図的に病的な構成として作られたものであり，実際に使われるプロトコル(Fiat-Shamir変換によるSchnorr署名など)に対する具体的な攻撃が見つかっているわけではない
- ROMでの証明は，明示した仮定と攻撃モデルのもとで対象の安全性を保証する．実装上の欠陥やモデル外の攻撃まで除外したことにはならない
- ROMを使わない構成との効率比較は，要求する機能とセットアップモデルに依存する．第11回のGroth16はCRSモデルで直接構成され，Fiat-ShamirやROMを必要としない

### 4.4 この批判的視点をどう位置づけるか

方式を読むときは，どこでランダムオラクルを使い，その仮定から何を示しているかを追おう．「安全性証明がある」という一言で済ませず，モデル・前提・実装を分けて確認する．この読み方は，後のPLONKやSTARKを評価する際にも使う．

### 4.5 IPの観点：対話が保証していた「順序」を失う {#rom-interaction-limits}

第1回のIP(対話型証明)に戻ろう．健全性は，偽の命題 $x\notin L$ に対して，どの不正な証明者 $P^*$ も，検証者の乱数を含む実験で高い確率では受理されないという性質だった．

$$\forall x\notin L，\ \forall P^*，\qquad
\Pr_{\rho_V}\bigl[\langle P^*,V\rangle(x)=1\bigr]\le\epsilon.$$

必要なら $P^*$ の乱数も確率に含める．IPでは，$P^*$ の計算能力を制限せずにこの性質を要求する．公開コイン型の場合，証明者がメッセージ $a$ を送った**後**で，検証者が新しいチャレンジ $c$ を一様に選ぶ．過去の記録を条件としても，次の乱数は新しく選ばれる．証明者はその $c$ に答える必要があり，都合が悪いから同じ実行の過去を書き換えることはできない．

Fiat-Shamirでは $c=H(x,a)$ を証明者自身が計算するため，$a_1,a_2,\dots$ を試して，望ましいハッシュ値が出た候補だけを提出できる．最終的に提出される $a$ を条件としたチャレンジは，独立な一様乱数とは限らない．ROMでも，各未問い合わせ入力への応答は一様だが，**その中から選んで提出する記録の確率分布**まで一様になるわけではない．対話型と非対話型では，健全性を測る確率実験が異なるのである．

たとえば，どの固定済み候補でも「有利なチャレンジ」の割合が高々 $2^{-k}$ となる単純な状況を考えよう．独立な新規オラクル応答を $Q_H$ 回試すなら，いずれかの試行が有利になる確率は合併界により高々 $\min(1,Q_H2^{-k})$ である．$k=20$ でも約100万回試せるなら，この上限はもはや小さくない．これは試行回数の影響を見る例であり，任意のプロトコルの健全性誤差がこの式になるという定理ではない．

計算能力に制限のない証明者なら，このような探索を効率性で制限できない．したがって，変換前の情報理論的なProofの健全性が，そのまま変換後にも残るとは考えない．Fiat-Shamirを使う非対話型構成では通常，効率的な敵対者に対するArgumentの健全性を，問い合わせ数や計算量とともに評価する．

### 4.6 公開コイン型と，一般のIPは同じ出発点ではない

Fiat-Shamirが直接置き換える対象は，検証者の公開ランダムチャレンジである．一般のIPでは，検証者が秘密の乱数を保持し，その一部だけをメッセージへ反映してよい．その乱数をすべて $H(\text{記録})$ で公開再計算できる値に置き換えると，証明者に与える情報そのものが変わる．

Goldwasser–Sipserは，[秘密コイン型IPを公開コイン型へ変換できること](https://www.cs.toronto.edu/tss/files/papers/goldwasser-Sipser.pdf)を示した．しかしこれはプロトコルの変換であり，元のメッセージをそのままハッシュへ置き換えてよいという結果ではない．ゼロ知識性や知識の抽出，ラウンド数，変換後のFiat-Shamirの健全性については，それぞれ条件を確認する必要がある．

同様に，$\mathrm{IP}=\mathrm{PSPACE}$ から「PSPACEの計算を何でもFiat-Shamirで安全な短い非対話型証明にできる」とは結論できない．この等式が述べるのは，対話とランダム化を許した証明系の表現力である．簡潔性，効率的な証明生成，ゼロ知識性，具体的な非対話化の安全性は別の要求である．

### 4.7 シミュレータは，実装より強い能力を使っていないか {#rom-simulation-limits}

第2回のSchnorrを思い出そう．公開鍵 $Y=g^w$ に対する受理条件は $g^z=aY^c$ である．ウィットネス $w$ を知らなくても，$c,z$ を先に選んで $a=g^zY^{-c}$ と置けば，受理される形の記録 $(a,c,z)$ を作れる．これは正直な検証者に対するシミュレーションの考え方である．**受理記録を作れることと，$a$ を先に送った後で相手のチャレンジへ答えられることは違う．** ここではウィットネスの知識について議論しており，公開鍵が群に属するかという言語の健全性だけの話ではない．

非対話化した記録には，さらに $c=H(x,a)$ が必要になる．プログラム可能なROMでのシミュレータは，未定義の入力への応答を適切に設定することで，この関係を成立させる場合がある．ただし，すでに問い合わせた点との整合性や，実際のランダムオラクルとの確率分布の差まで解析しなければならない．現実の証明者が，SHA-256の任意の出力を上書きできるという意味ではない．

また，forking lemmaで異なる実行のオラクル応答を変えるのは，知識の抽出を示す還元の中の操作である．ゼロ知識性のシミュレータが応答を設定する操作とは，目的が異なる．いずれも，実装に「ハッシュを変更するAPI」があるという説明ではない．

この違いは，[ROMにおけるゼロ知識性の定式化を比較した研究](https://www.iacr.org/archive/asiacrypt2009/59120414/59120414.pdf)でも扱われている．どのオラクルへのアクセスと設定権限をシミュレータに与えるかで，保証する性質が変わる．「シミュレータが存在する」だけで，現実の第三者も同じ公開ハッシュのもとで受理証明を生成できるとは言えない．

### 4.8 セットアップもオラクルもない非対話型ゼロ知識の壁 {#plain-model-nizk}

この問題は，ハッシュ関数の性能だけの問題ではない．共有参照文字列(CRS)，ランダムオラクル，事前の鍵配布などを持たない**プレーンモデル**で，一通の証明を送る非対話型ゼロ知識を考えよう．通常の定義のもとでは，このような仕組みを持つ言語はBPPに入るという制約がある．[Goldreich–Orenの研究](https://www.wisdom.weizmann.ac.il/~oded/PSX/oren.pdf)は，非自明なゼロ知識に対話が必要になる条件を整理している．

なぜこの制約が現れるのか．ここではシミュレータ $S$ が全入力上で多項式時間に停止する定式化で，考え方を追おう．入力 $x$ に対し，ウィットネスなしで $\pi\leftarrow S(x)$ を作り，通常の検証器 $V(x,\pi)$ を動かすアルゴリズムを考える．

- $x\in L$ なら，シミュレーションした証明は本物と識別できない．効率的な $V$ 自身も識別器なので，完全性により高い確率で受理する．
- $x\notin L$ なら，$S$ も単に証明を出力する効率的なアルゴリズムである．健全性により，高い確率では受理されない．

すると，証明者のウィットネスなしで $L$ を確率的多項式時間で判定できてしまう．対話型の場合，シミュレータが作った記録を見せても，新しく乱数を選ぶ検証者との実行にはならないため，この推論はそのまま使えない．

ROMやCRSモデルでは，シミュレータに許す資源が違う．プログラム可能なROMではオラクルを設定でき，CRSモデルではシミュレーション用の参照文字列と秘密情報を生成することがある．これは，固定された実環境で同じ能力を持たない証明者とは異なる実験なので，上のBPPへの推論をそのまま適用できない．

したがって，Groth16がROMを使わないことは，「追加の設定を何も使わずに非対話型ゼロ知識を実現した」という意味ではない．Groth16はCRSを使う．**標準モデルとプレーンモデルも同義ではない．** ランダムオラクルを理想化しない標準モデルで，CRSを仮定する構成はありうる．

### 4.9 一方向性・衝突耐性だけでは埋まらない隔たり

具体的なハッシュ関数には，有限長のコードや公開鍵などの記述があり，攻撃者はそれを見て計算できる．ランダムオラクルは問い合わせだけで利用する理想的な関数であり，攻撃者に利用可能な短い実装記述を渡しているわけではない．この差によって，入力と出力の特定の相関を狙う攻撃を，一方向性や衝突耐性だけでは排除できない場合がある．

CGHの反例に加え，Goldwasser–Kalaiは，[安全な3ラウンドの公開コイン識別方式でも，Fiat-Shamirで得た署名がどの効率的な関数族による実体化でも安全にならない例](https://eccc.weizmann.ac.il/eccc-reports/2003/TR03-015/index.html)を示した．これは「すべてのFiat-Shamir方式が破れる」という意味でも，「情報理論的に健全なすべてのIPに同じ反例がある」という意味でもない．反例の対象となる方式と性質を限定して読む必要がある．

本質的な問いは，対話が担っていた予測不能性と順序を，何という資源と仮定へ移したのか，ということである．PLONKやSTARKを読む際には，公開コイン型の元のプロトコル，オラクルへの問い合わせ能力，シミュレーションの権限，セットアップ条件を明記したうえで，変換後の健全性・知識の健全性・ゼロ知識性を個別に確認しよう．

## まとめと次回予告

今日は，対話をなくす変換と，その変換の安全性を扱うモデルを学んだ．手順，モデル，実装の三つを分けて振り返ろう．

- Fiat-Shamir変換:対話型プロトコルのチャレンジをハッシュ関数で代用することによる非対話化の仕組み
- Random Oracle Model:ハッシュ関数を理想化したモデルにおける安全性証明の考え方，forking lemma(第6回)がここで実際に使われること
- ROMの理論的な限界:CGHの反例が示す，ROMでの証明が万能の保証にならないことの理論的根拠
- それでもROMが実務で広く受け入れられている理由と，その批判的な評価の必要性

次回(第10回)は幕IIの最終回として，PCP定理とIOPの枠組みを扱う．これまで断片的に触れてきた計算量理論的な背景(IP=PSPACE，Cook-Levin定理)を，PCP定理という形で総括し，近似困難性研究とのつながりにも触れる．これにより，幕IIで整備したすべての道具が，幕IIIで実際のプロトコルを読むための準備として揃うことになる．
